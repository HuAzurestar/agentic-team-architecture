# 公司接入与用户交流 instruction 模板

这是可选公司 instruction，实际角色、授权和已配置入口以宿主为准。它不属于通用 skill，不自动安装运行配置或扩大权限。

## 首次配置

① 明确 `<Project-Manage>` 的确切位置、访问/写入方式、维护者，以及适用的 Git 分支和提交策略；仓库搜索根目录另行说明，不从候选目录猜选管理目录。

② 在 `project/<project-key>/project.yaml` 保存稳定仓库映射；已有环境配置先读取复用，只询问缺失、冲突、过期或扩大权限的部分。配置存在不证明环境可用。

③ 明确通知和决定入口的标识、维护者、优先级、回复关联和失败处理。可以使用用户指定并由用户 pin 的持久 issue；没有明确入口时不自行启用其他渠道。

④ 明确有效角色授权；提出者、业务负责人、决定者、执行者不同，未知项列为决策点，不把发言者、代录者或执行 Agent 自动当作业务负责人。

具体机器路径、账号与秘密由本地/平台绑定提供；此模板不实现配置发现器、凭据加载器或通知服务。

## 接入与重复核对

用户可通过已配置 socket 或直接向 orchestrator 提需求；保留原话、真实提出者、渠道、可获得的消息标识和时间，不要求重复提交。

创建内部任务或平台派发前，orchestrator 核对 Feature 标识、来源消息、已有 INT、范围、当前版本和既有任务。重复请求关联已有记录；范围增补或修正保留来源关联并按版本处理。相同编号不证明内容相同，含糊时询问，不静默合并或重复建任务。

不可访问的外部 issue 可以只保留业务标号，以实际收到的内容为依据，明确外部来源未核实，不编造链接、人员或批准。

## 推荐回复结构

按实际内容使用 A/B/C，短请求可精简，不为填满栏目编造选项或决定。

### A．我们理解要做什么

基于【对象与版本】，我们理解本次要实现：

① 【业务结果、主要边界和可观察的验收标准】。

② 【其他业务结果】。

请确认理解是否有误。尚不明确的是【具体歧义及影响】，此假设尚未当作已批准需求。

### B．需要您决定或讨论什么

① 对于【问题、对象及版本】：

- Ⅰ 推荐方案：【做法】；理由：【依据】；主要代价/风险：【已知影响】。
- Ⅱ 备选方案：【做法】；适用理由：【何时更合适】；主要代价/风险：【已知影响】。
- Ⅲ 若确有第三种选择：【做法、理由和影响】。
- 请决定：【准确范围】；批准后拟允许：【具体动作】。

② 其他问题使用相同分点方式；缺失的角色归属同样明确列点。

您可以逐项选择，另提方案，或指定某点单独讨论。一次回复可明确确认已列出的多项；确认需求理解不自动批准方案、未来版本或后续动作。未答复或含糊答复保持未决。

### C．依据已有授权，我们已决定什么

① 对于【对象及版本】，我们决定【内容】。实际决定者：【身份】；授权依据：【instruction/决定的版本与条款】；满足的条件：【具体说明】；理由与已知影响：【实际依据】。

② 【其他实际存在的自主决定】。

单独披露有效授权内的决定，不混入待批准项。无授权或条件不满足时转入 B；“简单”“有把握”“低风险”不产生权限。没有自主决定时省略 C。披露不授权重开、发布、部署或另开通知渠道。

## 持久 issue 交流

用户指定持久 issue 后，orchestrator 统一安排内容、版本和决定闭环；socket 按派发整理输入、投递和带回原话。直接向 orchestrator 提出的请求同样处理。

优先通知待决策事项；其他阻塞、范围变化、里程碑和验收可适量汇总，不默认逐任务刷屏。消息说明 Feature/任务、版本、问题与选项、证据及风险、允许动作和实际决定者，优先通过对应评论线程关联回复。

用户原话、来源、实际确认者、时间、对象版本和允许范围仍写入管理目录；issue 是交流入口，不覆盖正式记录。发送成功、实际收到、作出决定和执行分别记录。发送失败不自动启用未授权备用渠道；沉默、超时或校验通过不等于批准。

持续接收回复采用宿主已有且获授权的持久事件机制，记录目标 Agent、用户过滤、规则标识和续接方式；不能以单次运行退出后的后台进程冒充持久服务。本模板不新增 GATE 类别，不替代有效 START/COMPLETION 规则。
