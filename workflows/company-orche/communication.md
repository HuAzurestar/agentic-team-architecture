# 公司接入与用户交流 instruction 模板

这是可选公司 instruction，实际角色、授权和已配置入口以宿主为准。它不属于通用 skill，不自动安装运行配置或扩大权限。

## 首次配置

① 由开发机/runtime 初始化 Skill 的项目管理持久配置并提供明确引导入口，解析 PM 位置、写入方式和提交策略；机器路径不进入 Agent instruction，迁移后使用目标 runtime 的配置，不猜选管理目录。

② 在 `project/<project-key>/project.yaml` 保存稳定仓库映射；已有环境配置先读取复用，只询问缺失、冲突、过期或扩大权限的部分。配置存在不证明环境可用。

③ 由 runtime 的通知持久配置绑定工具、节点、路由及回复/失败处理。Agent 按真实流程形成带版本、目的和重要程度的事件，用户接收器决定订阅/展示；持久 issue 可作为一种 adapter 路由，不固化到角色。缺少实际接入时返回缺项。

④ 明确有效角色授权；提出者、业务负责人、决定者、执行者不同，未知项列为决策点，不把发言者、代录者或执行 Agent 自动当作业务负责人。

instruction 依赖用户设计理念和组织授权，不依赖具体生产环境；机器路径、网络节点和通知工具通过 Skill 的 runtime 持久配置解析。此稿不实现配置发现器、凭据加载器或通知服务。

## 接入与重复核对

用户可通过已配置 socket 或直接向 orchestrator 提需求；保留原话、真实提出者、渠道、可获得的消息标识和时间，不要求重复提交。

创建内部任务或平台派发前，orchestrator 核对 Feature 标识、来源消息、已有 INT、范围、当前版本和既有任务。重复请求关联已有记录；范围增补或修正保留来源关联并按版本处理。相同编号不证明内容相同，含糊时询问，不静默合并或重复建任务。

不可访问的外部 issue 可以只保留业务标号，以实际收到的内容为依据，明确外部来源未核实，不编造链接、人员或批准。

## `Align-Decide-Disclose`（对齐—决策—披露）规则

这是 notify 功能及 Agent 间、Agent 与用户之间需要汇报时的交流规则。先对齐背景，再提出希望对方作出的决定，最后披露已自主处理的事项；三部分服务实际交流，不是固定三栏表单。可省略空项，短答复不必强凑完整结构。

### `Align` — 对齐：背景和现状

说明【Feature／任务／对象与版本】、当前目标、已知事实、进展和相关约束；假设、歧义与待核实部分明确区分。只有需要澄清时才请求纠正，不为普通状态汇报重复索要批准。

示例：本轮目标为①……②……；目前完成……，受阻于……。我们暂按……理解，尚待核实的是……。

### `Decide` — 决策：希望接收方决定什么

① 对于【问题及准确版本】：

- Ⅰ 推荐方案：【做法】；理由：【依据】；主要代价／风险：【影响】。
- Ⅱ 备选方案：【做法】；适用理由及代价：【说明】。
- 如有实质第三方案再列Ⅲ，不为填满格式制造选项。
- 请决定：【具体范围】；决定后拟允许：【具体动作及条件】；必要时说明禁行动作。

其他问题同样逐项列出。接收方可逐项选、另提方案或单独讨论。对齐现状不等于批准方案，方案决定也不默认覆盖未来版本或后续动作；含糊回复保持未决。没有需对方决定的事项时省略本部分。

### `Disclose` — 披露：已自主决定／处理的报备

① 对于【对象及版本】，我们已自主决定【内容】／已执行【动作】。依据【有效授权及满足条件】，理由为【实际依据】；实际结果【证据／回执】，未完成或限制【如实说明】。

把“决定了什么”和“实际做了什么”分别表达。允许在已有自主权限内先处理后报备；没有实际执行的计划不写成已完成。超出权限或条件未满足时放入Decide请求决定，不用报备代替事前批准；不以“简单”“低风险”扩权。没有自主事项时省略本部分。披露不自动授权重开、合并、部署或另启渠道，适用GATE仍独立核对。

### 协作与投递

Agent间采用同样含义：Align对齐事实与输入版本，Decide提出希望对方在其权限内决定或接续的事项，Disclose交代自主处理及实际结果。提供材料、提出建议和获得批准分别记录。

组织内所有角色可提供事实和必要沟通；正式项目汇报、待决策请求和最终通知由socket汇总，runtime提供实际notify工具／路由。规则只组织消息内容，不实现投递、认证、重试或授权判断，也不改变事件信封／JSON字段契约。

## 通知与决定闭环（持久 issue 为路由示例）

用户指定持久 issue 后，orchestrator 提供正式Feature状态、对象版本与待决策材料并落实决定；socket负责汇总、最终通知、对话和带回原话。直接向orchestrator提出的请求同样保留来源和关联，不要求重发。

按实际流程保留 REQ/SOL 确认、GATE、行动预告、阻塞、范围变化及结果事件，并标注重要程度；接收器处理订阅、展示或汇总，不由角色静默丢弃流程事实。消息说明 Feature/任务、版本、问题与选项、证据及风险、允许动作和实际决定者，优先通过对应评论线程关联回复。

用户原话、来源、实际确认者、时间、对象版本和允许范围仍写入管理目录；issue 是交流入口，不覆盖正式记录。发送成功、实际收到、作出决定和执行分别记录。发送失败不自动启用未授权备用渠道；沉默、超时或校验通过不等于批准。

持续接收回复采用宿主已有且获授权的持久事件机制，记录目标 Agent、用户过滤、规则标识和续接方式；不能以单次运行退出后的后台进程冒充持久服务。本模板不新增 GATE 类别，不替代有效 START/COMPLETION 规则。
