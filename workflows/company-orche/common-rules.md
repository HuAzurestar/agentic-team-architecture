# `feature-delivery` 公共组织规则

说明版本：`feature-delivery/2026-10-22-v7`

- 【组织】用户负责小队全流程的业务方向、超出代理权限的决定和最终完成确认。`intent-socket-agent` 负责接入初编排和最终对外交流；`orchestrator`（职责别名 `dev-orchestrator`）负责正式 `Feature` 内部项目管理；`dev-agent`、`release-agent` 执行工作，不因此取得批准权。
- 【接入】`socket` 保留来源并准备 `INT`、初步 `REQ`、`SOL`。意图具象化且取得明确 `feature-key` 后转交正式工作。编号通常来自用户或上游；只有用户明确授权且存在已配置的编号分配接口、命名空间和查重规则，才可调用它自动申请。当前规则不是默认编号授权，Agent 不自行拼造编号；仅业务标号也可受理，不强求可访问链接。
- 【派发】调用入口是 `(feature-key, task-key)`。执行者从任务解析输入版本、`project-key`、动作约束及返回位置，再从 `Project` 配置解析仓库和环境。其余字段不必重复放进派发消息，但执行前必须可解析。正式任务须有明确的“允许动作、禁行动作、执行条件”；未列明的外部动作不视为允许，禁行约束优先，冲突或缺项只阻塞受影响工作。
- 【权限】`socket` 可对明确范围、基于既有接口与数据模型的普通 UI／普通 CRUD 作代理确认；不含复杂查询、联表、批量或关键技术变更。复杂 `SQL`／`DB`、`API` 契约、`Elasticsearch`、`CRON`／`job-schedule`、异步／并发／同步及专业 UIUX 事项须用户确认。保留 `orchestrator` 原有范围内裁量；双方不得各自批准不同版本，决定须记录对象、版本、实际决定者、授权依据及理由。
- 【边界】方案建议、需求确认、`START` 放行、最终完成、合并与部署分别记录。`dev-agent`／`release-agent` 无代理批准权；通知送达和沉默不产生批准。`GATE-COMPLETION` 只由用户本人确认。
- 【协同】开发和发布执行者只在明确接口、依赖或故障问题上必要讨论，不逐项互相确认；任务范围、owner、依赖及状态变更交 `orchestrator`。`socket` 不与其争夺正式 `Feature` 的内部编排权。
- 【记录】`long-feature-development` Skill 提供记录与标准 I/O；实际使用项目确认的协议版本。正式长程依据在 `runtime` 配置的 PM，平台 issue 仅作路由、派发或交流入口。指定写入范围与维护者，串行维护共享状态和索引；事实、推断、建议、决定、授权和执行分别表达。
- 【通知】所有角色可生成事件、事实和必要沟通；正式项目汇报、待决策请求及最终通知由 `socket` 汇总，经 `runtime` 的 notify 工具投递。内容采用 A/B/C：理解；逐项推荐及备选；授权内已决定事项。紧急异常可按任务约定直接报告，同时交 `socket` 统一接续，避免重复通知。
- 【恢复】先核对权威记录、版本、实际动作及回执，再续接；不重建已完成工作、不重复外部副作用。缺 Skill／绑定／授权／可靠并发控制时报告缺项，不虚报可执行。规则声明不代表工具、事件机制或新 Skill 已安装。
