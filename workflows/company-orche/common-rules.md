# `feature-delivery` 公共组织规则

说明版本：`feature-delivery/2026-10-22-v11`

- 【组织】用户负责小队全流程的业务方向、超出代理权限的决定和最终完成确认。`intent-socket-agent` 负责接入初编排和最终对外交流；`orchestrator`（职责别名 `dev-orchestrator`）负责正式 `Feature` 内部项目管理；`dev-agent`、`release-agent` 执行工作，不因此取得批准权。
- 【接入】来源可为 `NO-FEAT` 原始 `INT` 或直接陈述，`REQ`／`SOL` 可选；取得正式编号时同步迁入已有相关设计及版本／决定／依赖，保留来源映射并查重。编号由用户指定，或在用户明确选择自动编号后经 runtime 绑定的 Multica 专用项目创建／复用 issue，使用实际返回的 issue 标号；不自编、不使用项目 UUID 作 FEAT 号。未取得外部编号不创建正式目录，仅业务标号也不强求来源链接。
- 【派发】PM 子任务入口保持 `(feature-key, task-key)`；一个 Multica 执行 issue 可按同一 Feature、同类工作及内聚模块承载 1～5 个明确子任务，逐项解析输入、Project、允许／禁行／条件并逐项验收，不新增虚构汇总 task。FEAT 及执行 issue 归 runtime 绑定的“自动开发项目”，执行 issue 全部直接隶属 FEAT issue，按类型／模块命名。模块默认 `(all)`，不证明可并发；依赖、写入范围、环境及实际排他共同决定并发。禁行约束优先，缺项只阻塞受影响工作。
- 【权限】`socket` 可对明确范围、基于既有接口与数据模型的普通 UI／普通 CRUD 作代理确认；不含复杂查询、联表、批量或关键技术变更。复杂 `SQL`／`DB`、`API` 契约、`Elasticsearch`、`CRON`／`job-schedule`、异步／并发／同步及专业 UIUX 事项须用户确认。`orchestrator` 负责组织、核查及落实决定，不自行批准 `GATE`；不得各自批准不同版本，决定须记录对象、版本、实际决定者、授权依据及理由。
- 【开发与反馈】DEV-REFINE／DEV-BUG-FIX／DEV-REFACTOR都是DEV（type: development）的子类；DEV内TDD、单元、局部集成和调试测试属于DEV，允许同上下文实施，不冒充独立TEST。独立TEST负责业务、回归及统一验证。REVIEW／TEST发现产出FEEDBACK，不直接造INT；分类处置可产生ADVICE／BUG，需处理的项经本次SOL及确认、对应START进入DEV子类；不采纳建议或环境问题可不启动DEV。新增类型是否可写入以实际Skill协议为准。
- 【上下文】`DEV`、`REVIEW`、`TEST`、`DOCS` 各自必须在独立、干净的上下文进程执行，一次只做对应工作；同一 Agent 可以运行不同独立进程，换任务名／加提示／串行执行不等于上下文隔离，禁止将 DEV 会话继续用作 REVIEW、TEST 或 DOCS。`INT`、`REQ`、`SOL` 的设计可共用上下文；设计与确认必须分开，确认使用新的干净上下文，只读取显式版本化材料，不继承起草对话。保留实际 run／session 标识及工作类型；无法证明隔离时报告缺项，不冒充独立执行。
- 【GATE】所有 `GATE` 默认只由用户本人批准，`GATE-COMPLETION` 永不代理。唯一例外：`socket` 在独立于起草的确认上下文中，逐项确认本轮所有适用 `REQ` 和 `SOL` 均满足其简单事项特许条件，且全部确认者都是 `socket`、准确版本未变；同时确认本阶段输入已收口且无未处理 `INT`，才可由 `socket` 批准对应 `GATE-START-X`。混合用户／其他角色确认、不满足简单条件或收口未确认时，仍须用户批准 START；`orchestrator` 无代理 START 权。
- 【收口】记录本轮设计版本、全部 socket 确认引用、输入批次／截止点、明确收口依据及未处理INT及影响本轮范围的未处置FEEDBACK检查。收口依据可为用户说明或已配置来源的有效批次结束信号，不能用沉默、瞬时空队列或猜测代替，也不承诺未来永无新意图。新INT或FEEDBACK到达后核对其影响；改变当前放行范围／版本时先停止受影响的未执行动作，重走相应设计确认和新轮次 START，不覆盖旧批准历史。
- 【边界】方案建议、REQ／SOL 确认、GATE 批准、合并与部署分别记录。`dev-agent`／`release-agent` 无代理批准权；`REQ`／`SOL` 确认、`ADVICE`／`BUG` 处置决定和发布批准请求均交 `socket`，由其按特许范围决定或请求用户；技术执行者提供分析，`orchestrator` 分类组织并核验／登记实际决定，发布执行找 `release-agent`。`orchestrator` 可核验／登记关口条件和实际批准回执，不能把检查通过或任务 DONE 当作授权。通知送达和沉默不产生批准。
- 【协同】开发和发布执行者只在明确接口、依赖或故障问题上必要讨论，不逐项互相确认；任务范围、owner、依赖及状态变更交 `orchestrator`。`socket` 不与其争夺正式 `Feature` 的内部编排权。
- 【记录】`long-feature-development` Skill 提供记录与标准 I/O；实际使用项目确认的协议版本。正式长程依据在 `runtime` 配置的 PM，平台 issue 仅作路由、派发或交流入口。指定写入范围与维护者，串行维护共享状态和索引；事实、推断、建议、决定、授权和执行分别表达。
- 【通知】所有角色可生成事件、事实和必要沟通；正式项目汇报、待决策请求及最终通知由 `socket` 汇总，经 `runtime` 的 notify 工具投递。notify及需要汇报的Agent间／Agent与用户交流采用 `Align-Decide-Disclose`（对齐—决策—披露）规则：`Align`提供现状、背景、对象版本及未决假设；`Decide`明确希望接收方作出的决定、推荐／备选及决定后的动作；`Disclose`报备已在授权内自主决定或执行的事项、依据与实际结果，区分已决定、已执行和未完成。按实际内容省略空项，简短答复无需强凑三段；披露不产生追溯授权或绕过GATE的权限。紧急异常可按任务约定直接报告，同时交 `socket` 统一接续，避免重复通知。
- 【恢复】先核对权威记录、版本、实际动作及回执，再续接；不重建已完成工作、不重复外部副作用。缺 Skill／绑定／授权／可靠并发控制时报告缺项，不虚报可执行。规则声明不代表工具、事件机制或新 Skill 已安装。
