# 01 架构划分（v2）

> 组织与角色的分层。本文档定义 OPC 的顶层结构：**OPC → BG → C..O**，并给出 BG 的完整组织与结构。

## 1. 分层模型

```
OPC（One Person Company）= 一位 CEO + 一个 AI 团队运营一家公司（可拓展到多人多 OPC，各 BG 有各自的 CEO）
└── BG（Business Group，事业群）= OPC 的组织单元
    ├── BG 成员：AS、HR、CPO、CTO、COO、CKO、Assistant AS
    └── 中心：PC / TC / OC —— 分别由 CPO / CTO / COO 所属
```

- **OPC**：顶层形态，唯一不变。
- **BG**：业务组织单元，成员为 **AS、HR、CPO、CTO、COO、CKO、Assistant AS**（7 个 Agent 角色；CEO 属 BG 但不计入成员数）。一个 OPC 可含多个 BG，各自命名。
- **中心**：CPO、CTO、COO 同时作为中心的**所属（head）**，对应 **PC 产品中心 / TC 技术中心 / OC 运营中心**；中心是 BG 之下的第二层组织。
- **C..O**：BG 的功能负责人。当前定义 CPO（产品）、CTO（技术）、COO（运营）、CKO（知识）；BG 下若要加成员，除 HR/AS/CKO 外就是其它 C..O。

> **架构与实现分离**：架构层只定义 **BG / 中心**。"小队（squad）"是实现层概念——在 Multica 中是为 issue 分派服务的 @ 工具，不属于架构；见 [docs/06-multica-landing.md](06-multica-landing.md)。

## 2. BG 组织架构

BG 采用**扁平成员制**。**CEO 属于 BG，是 BG 的实际掌舵人与最终决策者**；BG 名义 lead 是 **AS**（代行 CEO，CEO 可不在场）。CPO / CTO / COO 同时是中心（PC / TC / OC）的所属；HR、CKO、AS 为 BG 直属。

```
BG（组织单元；BG 成员 7 = AS、HR、CPO、CTO、COO、CKO、Assistant AS；CEO 属 BG 不计入）
├── CPO — BG 成员；兼 PC 产品中心所属：负责产品的成色设计
├── CTO — BG 成员；兼 TC 技术中心所属：负责如何实现产品
├── COO — BG 成员；兼 OC 运营中心所属：负责产品的长期执行
├── CKO — BG 成员（直属）：管理 skills / 知识 / 文档 / issue 关闭
├── HR  — BG 成员（直属）：人事与架构调整（agent 归属、skill 配置），有管理权不可越权
└── AS  — BG 成员（直属）：CEO 代理人 / BG 名义 lead，推动工作；可蠢不可越权
    └── Assistant AS — BG 成员（AS 二级）：触发器 + 显式红线简单监督，向 AS 负责
```

### 2.1 各成员定位速览

| 角色 | 定位 / 所属 | 核心职责 |
| --- | --- | --- |
| CPO | BG 成员；PC 产品中心 | 产品的**成色设计**（需求、体验、质量） |
| CTO | BG 成员；TC 技术中心 | **如何实现**产品（架构、研发、交付） |
| COO | BG 成员；OC 运营中心 | 产品的**长期执行**（运营、增长、完整落地） |
| CKO | BG 成员（直属） | 管理 skills / 获取资讯 / 文档与 issue 管理（关闭权限在 CKO） |
| HR | BG 成员（直属） | 人事与架构调整：agent 归属、skill 等配置；管理权但不越权 |
| AS | BG 成员（直属） | CEO 代理人 / BG 名义 lead：推动工作；杂务；可蠢不可越权 |
| Assistant AS | BG 成员（AS 二级） | 触发器 + 显式红线简单监督；向 AS 负责（不向 CEO） |

> 各角色完整规格（权限、产出、红线）见 [docs/02-boundaries.md](02-boundaries.md)。

### 2.2 TC 技术中心（CTO 下属）细分角色

CTO 下属为各层执行单位。技术研发覆盖：技术规划、研发（前后端）、质量审查。**运维与安全审批不属于技术职能，分属运营中心（OC）——产品上线相关交由运营**。TC 技术中心是组织单元，负责人为**技术总监 / 技术主管**（总监/主管类角色，向 CTO 汇报）。

```
TC 技术中心（负责人 = 技术总监 / 技术主管，总监/主管类）
├── 技术规划　Architect 架构师—— 为技术实现划分界限
├── 研发（统一执行角色，普通）—— 前端 / 后端通用实现
└── 质量审查（普通）—— Code / Plan / Testing 三视角经不同 skill 配置拆分
               （界面要求高时补：UI / UX 审查视角）
```

- **中心负责人**：TC 技术中心由**技术总监 / 技术主管**（总监/主管类角色）担任负责人，向 CTO 汇报，统筹技术中心执行与交付。
- **普通角色**：职员岗位统一用普通岗名（Architect、研发、质量审查等），**不设前端 / 后端高级岗**；"高级"仅指模型成本档（Senior 档，见 [docs/03-intelligence.md](03-intelligence.md)），与岗位层正交。**运维 / 安全审批已移出 TC，归运营中心（OC）**。
- **研发统一**：FSE / FE / BE 三拆合并为**一个研发角色**（普通执行，前后端通用实现）；前端、后端由**同一研发角色**承担，不设前端 / 后端高级岗。
- **质量审查三视角（skill 拆分）**：Code（代码质量）、Plan（计划质量）、Testing（极端情况/响应）三视角**不设独立岗位**，由同一质量审查职能经**不同的 skill 配置**拆分实现；界面要求高时补 UI / UX 审查视角。
- **算法（AE）**：算法问题更难，与前后端协作过多容易造成**上下文危险**——原则上**单独设一个中心**（如 AC 算法中心），不与前后端混编。v2 先记录此原则，具体结构后续定义。
- **PC / OC 细分**：初步定义见下（§2.3、§2.4），可按需增减。**运维（环境 / 部署 / 监控）与安全审批（发布审批）归运营中心（OC）**，由 OC 的**上线审核专员 / 质量风控专员**承接发布审批。

### 2.3 PC 产品中心（CPO 下属）细分角色

```
PC 产品中心（负责人 = CPO）
├── PM 产品经理—— 输出 PRD（需求文档）、业务流程图、原型图；跟进项目全生命周期
├── Product Assistant 产品助理—— 协助 PM 收集整理需求、竞品分析、编写日常文档、跟进项目排期
└── UI/UX 设计师—— 产品界面视觉设计、交互体验设计、设计规范制定
```

### 2.4 OC 运营中心（COO 下属）细分角色

```
OC 运营中心（负责人 = COO）
├── 上线审核专员 / 质量风控专员（Release / Compliance Specialist）—— 上线前最后一道关：发布流程合规、安全扫描结果、回滚预案、各方签字确认
├── 产品运营 / 活动运营（Product / Campaign Operator）—— 日常线上活动策划、用户生命周期管理、版本发布后业务数据跟踪与复盘
└── 内容运营 / 编辑（Content Operator / Editor）—— 平台内容生产、审核、日常发布与媒体矩阵维护
```

## 3. 汇报线与决策

> **统一口径**：**CEO 属于 BG，是 BG 的实际掌舵人与最终决策者**；BG 名义 lead 是 **AS**（代行 CEO，CEO 可不在场）。AS 有向 CEO 主动汇报的义务。该模式可迁移到多人协作（多个 BG / 多位 CEO）。

- **CEO 是最终决策者**：任何重要议题最终由 CEO 确认。
- **AS（CEO 代理人 / BG 名义 lead）**：AS 是 CEO 的代理人（**不对应某个具体的人**），只推动 CEO **明确命令**；CEO 未明确表示的事项不得擅自行动，需整理信息、定期汇报。主要职责：推动工作、防止停摆、管理在办任务、确认推进进度。**AS 下设 Assistant AS（二级能力/助理）**——执行高频简单推动，遇阻塞 push 不动时上报 AS 并告知严重性；**Assistant AS 向 AS 负责、不向 CEO 负责（唯一不向 CEO 负责的角色，充当触发器 + 显式红线简单监督）**。
- **HR（不直接对话 CEO）**：HR 管理旗下集群人力与 Agent 配置（模型参数、skill 归属），与 C..O 协商调度资源、节约成本、**评估成本**；直接与 C..O、AS 对话，**不和 CEO 对话**。**人事变动（运行时 / Agent / Skill / 参数配置 的增删与变更）须 CEO 批准。**
- **C..O（向 CEO 直接汇报）**：CPO / CTO / COO / CKO 管理旗下职责；虽有推动作用，但遵循"少动"原则；职责内拥有**裁量权**，范围来自对 CEO 意图的揣摩——辨别核心内容，避免意图被曲解或错误执行。跨中心冲突走升级机制（见 [docs/02-boundaries.md](02-boundaries.md)）。
- **CEO 未决策 = 项目停摆**：升级至 CEO 后若暂未决策，视为**停摆**，由 **AS 记录**并在**定期汇报**时统一通知 CEO，避免任务长期停摆。C..O 超时可凭**裁量权先行处理**，但需**高层一致通过**（**高层会议**，见 [docs/02-boundaries.md](02-boundaries.md) §3）并**上报 AS**。

## 4. 扩展与复制

- **多 BG**：以 BG 为模板复制；每个 BG 命名（如 BG A、BG B），成员结构相同。
- **BG 内加角色**：除 HR / AS / CKO 外，新增成员一律是 C..O 形态（如 CFO、CMO），各对应一个中心（如 FC 财务中心）。
- **BU（事业部）**：跨 BG/产品中心的矩阵单元，v2 仍为占位概念，后续版本定义。
- **BG 定制（模板 → 实例）**：架构中的角色是**模板**；实际创建 BG 时按业务实际情况调整（写论文 / 文职 / 硬件 / 游戏各不相同）。创建前**向 CEO 询问**：这个 BG 需要哪些职能、哪些角色、每个角色需要强到什么程度；确定后把**三级架构（BG / 中心 / 角色）**发给 CEO，**CEO 同意后开始组织**。
- **定制示例**：论文型 → 研究中心 **RC**（**CRO 首席研究官**，重算法 / 数据 / 测试，可能无运营、无前端、无架构师）；文职 → 数据处理师 + 纠正文风 / 思潮的部门；硬件 → 硬件工程师 / PID 工程师；游戏 → 前端加强 + 高并发服务器组织 + 运营加强。

## 5. 命名规则与职级体系

外企职级体系**仅作参考**。OPC 模式不需要过高的职级栈，采用**三级版本**：职级三大层（扁平化）+ 级别三级（模型成本档位）。

### 5.1 三级职级（自高到低，扁平化）

| 层级 | 职级 | 说明 |
| --- | --- | --- |
| 最高一级 | 总裁 / 执行总裁 / 副总裁（CEO / EVP / VP） | 公司 / 部门最高管理；扁平化——VP 级不细分上下级 |
| 中间一级 | 总监 / 经理（Director / Manager） | 部门 / 团队管理；扁平化——技术、产品各一个 D / M，不分级 |
| 最低一级 | 职员 | 执行岗，不使用专用头衔词即可 |

> **职级 = 岗位层**（上下级语义），与**级别（模型成本档）正交**：一个岗位可以跑任一成本档的模型。**当前使用**：v2 角色主要落在**最高一级（EVP）**与**最低一级（职员）**；**中间一级（Director / Manager）**当前由 TC 技术中心的负责人（技术总监 / 技术主管）使用；**VP / SVP 层为多 BG / BU 扩展预留**（SVP 属职级语义，与成本档无关）。

### 5.2 级别三级（= 模型成本档位）

每个角色可挂 **Assist（助理）/ 普通（标准）/ Senior（高级）** 三档模型，与"大小智能管理"的模型成本档位结合（见 [docs/03-intelligence.md](03-intelligence.md)）：

| 级别 | 模型定位 | 成本特征 |
| --- | --- | --- |
| Assist（助理） | 最便宜的模型 | 以 free 为目的 |
| 普通（标准） | 初级生产模型 | 有一定价格，频繁使用可以承受 |
| Senior（高级） | 高级生产模型 | 价格极高，频繁使用无法承受 |

> **级别 = 模型成本档**（贵 / 便宜），与职级（岗位层）正交：说"高级 / Senior"时若指模型即本表，若指岗位即 §5.1 职级语义。

### 5.3 在本架构中的应用

- **BG 成员（CPO / CTO / COO / HR / AS / CKO）**：位于**最高一级（EVP）**。CPO / CTO / COO 分别对应 PC / TC / OC 中心的 EVP；HR 对应 CHO（首席人事官）定位；CKO 对应 CKO（首席知识官）；AS 为 CEO 的代理人 / BG 名义 lead。
- **TC 技术中心**：**技术总监 / 技术主管**（负责人）位于**中间一级（总监 / 主管）**，使用 Head / Director / Lead / Manager 类头衔；细分角色（Architect、研发、质量审查）位于**最低一级（职员）**——岗位名统一为普通名，不设前端 / 后端高级岗；"高级"仅指模型成本档（Senior 档），可按 Senior / 普通 / Assist 三级细分。
- **新增角色**：按职责所在层级选用头衔——最高级用 C..O / EVP 系列；管理层用 VP / Director / Manager 系列；执行层用普通岗名。
