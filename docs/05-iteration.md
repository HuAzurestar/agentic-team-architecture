# 05 可自我迭代（v2）

> 架构自身如何持续演进：节奏、反馈闭环、版本演进。

## 1. 迭代节奏

- **默认**：双周迭代（可单周）。节奏由 AS 推动（**限于 CEO 确认的规划**）、各线配合；关键决策由 CEO 确认。
- 每迭代四步循环：**规划 → 执行 → 评审 → 复盘**。
  - 规划：对齐范围、优先级、分工（各线参与，AS 推动）。
  - 执行：按 [04-collaboration.md](04-collaboration.md) 的价值流推进。
  - 评审：评审关键交付物（成色定义、实现、运营方案）。
  - 复盘：结果 vs 目标，产出改进项。

## 2. 反馈闭环

| 反馈源 | 信号 | 归口 | 处置 |
| --- | --- | --- | --- |
| 用户/数据 | 反馈、留存、转化 | CPO / COO | 进入需求池，调整成色与运营 |
| 缺陷 | 线上缺陷 | CTO | 修复 + 回归 |
| 内部协作 | 阻塞、越权、沟通成本 | AS / HR | 复盘沉淀改进项 |
| 智能分档 | 成本/质量失衡 | HR + 各 C..O | 调整 [03] 档位与成本台账 |
| 边界问题 | 权限模糊、越权 | HR | 更新 [02] 边界 |

> 闭环要求：每个信号都有归口角色与下一步动作，不允许只记录不处置。

## 3. 架构版本演进

- 版本号 `vX.Y`，记录在各文档标题与本文档"变更记录"。
- **v2**：当前版本。新增基础概念层（00）、边界管理（02）、大小智能管理（03）；组织单元为 **BG**（无 CEO，成员：CPO/CTO/COO/HR/AS）。
- **v2.x（小版本）**：角色职责微调、分档参数更新、协作流补充。
- **v3（大版本）**：多 BG、BU 正式化、运营线展开、新增 C..O 等结构性变化。

### 演进流程

1. 复盘/评审中提出变更建议（含动机与影响范围）。
2. 个人裁决 + 相关线负责人评估。
3. 同步更新 README 与 docs/00-05 相关文档。
4. 记录到本文档"变更记录"。
5. 按云↔本地同步规则（见 README）提交并推送。

## 4. 团队自身迭代

- **角色与边界**：按 [02-boundaries.md](02-boundaries.md) 的边界管理原则调整；AS/HR 的"可蠢不可越权"红线必须持续守住。
- **智能分档**：按 [03-intelligence.md](03-intelligence.md) 的衡量指标持续调档。
- **协作与流程**：复盘发现的低效环节优先改进。
- **文档**：任何变更必须同步更新本仓库对应文档，保持架构文档始终最新。
