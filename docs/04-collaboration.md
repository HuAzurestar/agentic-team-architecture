# 04 协作模式（v2）

> 产品 / 技术 / 运营 / 人事 / 行政之间的协作流与跨中心协同。

## 1. 核心价值流

```
产品成色（CPO · PC 设计） → 技术实现（CTO · TC 交付） → 长期执行（COO · OC 运营） → 反馈回流
```

| 阶段 | Owner | 参与 | 关键动作 | 出口物 |
| --- | --- | --- | --- | --- |
| 成色设计 | CPO（PC 产品中心） | CTO、COO、AS | 定义产品成色、需求、验收标准 | 产品定义 + 验收标准 |
| 技术实现 | CTO（TC 技术中心） | CPO、COO | 技术方案、研发实现、交付 | 可运行的实现 |
| 长期执行 | COO（OC 运营中心） | CPO、CTO | 运营执行、增长留存、完整落地 | 运营数据 + 执行记录 |
| 反馈回流 | 各中心 | 用户、AS、CEO | 用户/数据/缺陷反馈回流，进入下一轮 | 反馈汇总 → 迭代输入 |

### 交接规则

- **核心流程固定**：PC 设计方案 → TC 设计与开发 → OC 审核并上线、开始运营——这是总流程，**CEO 视角下不可改**。该流程的**产品由 CEO 下发或确认创建**；**AS 跟进推进**。
- **成色设计 → 技术实现**：CPO 交付"要什么"（定义 + 验收），CTO 决定"怎么做"。
- **技术实现 → 长期执行**：CTO 交付可用实现，COO 接手运营执行。
- **驳回机制**：下游发现问题可**驳回**，让上一流程重新处理。
- **严重问题升级**：职员搞不定 → 升级 → 由高职能**开会处置**，决定产品去留。
- **中心内部全权**：各中心内部如何运作（方案是否直接开发、要不要严格审核、重做还是驳回需求、是否启用高级职员）由**主管（CPO / CTO / COO）全权决策**，CEO 不干涉。
- **全程推进**：AS 推动各阶段按计划进行（**限于 CEO 已确认的事项**），跨中心阻塞由 AS 督办并上报 CEO 确认。
- **人事配置**：HR 在变更发生时调整 agent 归属与 skill 配置（如某个阶段需要更强模型/更多 Skill）。

### 1.1 研究价值流（新内容）

针对**新内容**（新方向 / 新结论 / 算法 / 数学证明等）的研发流程，**有别于产品主流程（PC→TC→OC）**：

```
产品（PC）列出新需求、定下研究基准 → RC 研究（论文调研 + 独立研究）→ CKO 整理成研究成果（edit / 归档）
```

| 阶段 | Owner | 参与 | 关键动作 | 出口物 |
| --- | --- | --- | --- | --- |
| 列需求 / 定基准 | CPO（PC 产品中心） | CRO、CKO | 明确新需求、研究目标与基准 | 需求 + 研究基准 |
| 研究 | CRO（RC 研究中心） | CKO（skill 支撑） | 阅读开源论文（下载/阅读/总结）、独立研究（算法 / 证明 / 分析） | 研究结论 / 草稿 |
| 整理归档 | CKO | CRO | 把研究成果整理成正式文档（edit），归档进知识库 / 文档库 | 研究成果（定稿） |

- **研究基准由 PC 定**：PC 列需求、定基准；RC 独立研究，不替 PC 改需求。
- **成果归口 CKO**：研究成果的 edit / 归档由 **CKO 负责**（研究结论是否定稿、如何存档由 CKO 整理）。
- **skill 支撑**：RC 阅读论文所需 skill（检索 / 下载 / 摘要）由 **CKO 协助检索**，HR 配置挂载。
- **研究结果进入主流程**：研究成果可成为下一轮 PC→TC→OC 的输入，或直接沉淀为知识。

## 2. 跨中心协同

- **产品 × 技术**：CPO 定义成色，CTO 实现；边界冲突（如"成本 vs 质量"）由双方协商，不成升级。
- **技术 × 运营**：CTO 保证可运行与稳定，COO 负责执行与增长；线上问题按严重级联动处理。
- **产品 × 运营**：CPO 定成色基准，COO 在基准内做长期执行；运营反馈回流给 CPO 调整成色。
- **人事 × 各中心**：HR 负责 agent 归属、skill 配置；配置变更需通知受影响中心负责人。
- **行政（AS）× 各中心**：AS 推动进度、处理杂务；不替代业务决策。

## 3. 升级机制

1. 相关 C..O 协商 → 2. AS 推动协调（限于 CEO 已确认范围内）→ 3. **CEO 最终确认**。
- **CEO 超时未决策** → 视为项目停摆，由 AS 记录并在定期汇报时统一通知 CEO；C..O 超时可凭裁量权先行处理，但需**高层一致通过**（**高层会议**，见 [docs/02-boundaries.md](02-boundaries.md) §3）并**上报 AS**。
- 越权（红线）即升级为事故，立即纠正并复盘。
- 升级必备信息：问题、影响、已尝试方案、需要的决策。

## 4. 例行同步

| 活动 | 频率 | 参与者 | 目的 |
| --- | --- | --- | --- |
| 规划对齐 | 每迭代开始 | 各中心 | 对齐范围与优先级 |
| 站会/进度同步 | 每日或按需 | 各中心 + AS | 同步进度、暴露阻塞 |
| 评审 | 迭代中 | 相关中心 | 评审关键交付物 |
| 复盘 | 迭代结束 | 全员 | 结果复盘 + 改进项 |

> 迭代节奏与复盘机制见 [docs/05-iteration.md](05-iteration.md)。
