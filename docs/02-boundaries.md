# 02 边界管理（v2）

> 定义每个角色的权限边界、红线与升级机制。核心原则：**可以蠢，不能越权**。

## 1. 角色规格与边界

每个角色字段：定位 / 负责线（二级所属）/ 职责 / 关键产出 / 权限（能做）/ 红线（不能做）/ 协作方 / 衡量指标。

> 角色档位按 [01-org-structure.md](01-org-structure.md) 的命名规则定位：BG 成员（CPO/CTO/COO/HR/AS）为 **EVP 级**；TC 技术中心 **squad 负责人（技术总监/技术主管）** 为**总监/主管级**；其余 TC 细分角色为**职员级**（可按 Senior / - / Assist 三级细分）。

### 1.1 CPO —— 产品负责人（Chief Production Officer）

- **定位**：BG 成员，兼 **PC 产品中心**（二级小队）所属；负责产品的**成色设计**。
- **职责**：产品方向与体验设计、需求定义、质量把关、产品验收；**了解下属职员擅长/不擅长、适合/不适合的模型**，配合 HR 准确派发任务（见 [03-intelligence.md](03-intelligence.md)）。
- **关键产出**：产品定义、需求与验收标准、成色（质量）基准。
- **权限**：职责内拥有**裁量权**，范围来自对 CEO 意图的揣摩——辨别核心内容，避免意图被曲解或错误执行导致结果不符 CEO 战略预期；在产品线内决定"做什么、做成什么样"。
- **红线**：不直接决定技术实现方案（属 CTO）；不做长期运营执行（属 COO）；遵循"少动"原则，不越权行事。
- **协作方**：CEO（直接汇报）、CTO、COO、HR、AS。
- **衡量指标**：产品成色/质量、需求交付、用户反馈、与 CEO 预期一致性。

### 1.2 CTO —— 技术负责人（Chief Technology Officer）

- **定位**：BG 成员，兼 **TC 技术中心**（二级小队）所属；负责**如何实现**产品。
- **职责**：技术架构、研发实现、技术交付、稳定性；**了解下属职员擅长/不擅长、适合/不适合的模型**，配合 HR 准确派发任务（见 [03-intelligence.md](03-intelligence.md)）。
- **关键产出**：技术方案、实现代码/系统、交付物。
- **权限**：职责内拥有**裁量权**，范围来自对 CEO 意图的揣摩——辨别核心内容，避免技术实现偏离 CEO 战略预期；在技术线内决定"怎么做、用什么实现"。
- **红线**：不改写产品定义（属 CPO）；不接管运营执行（属 COO）；遵循"少动"原则，不越权行事。
- **协作方**：CEO（直接汇报）、CPO、COO、HR、AS。
- **衡量指标**：实现质量、交付效率、系统稳定性、与 CEO 预期一致性。

### 1.3 COO —— 运营负责人（Chief Operations Officer）

- **定位**：BG 成员，兼 **OC 运营中心**（二级小队）所属；负责产品的**长期执行**。
- **职责**：运营执行、增长与留存、长期执行闭环；**了解下属职员擅长/不擅长、适合/不适合的模型**，配合 HR 准确派发任务（见 [03-intelligence.md](03-intelligence.md)）。
- **关键产出**：运营方案、执行记录、运营数据。
- **权限**：职责内拥有**裁量权**，范围来自对 CEO 意图的揣摩——辨别核心内容，避免长期执行偏离 CEO 战略预期；在运营线内决定"如何长期执行"。
- **红线**：不改写产品成色定义（属 CPO）；不重造技术实现（属 CTO）；遵循"少动"原则，不越权行事。
- **协作方**：CEO（直接汇报）、CPO、CTO、HR、AS。
- **衡量指标**：运营指标（留存/增长/转化）、执行闭环完整性、与 CEO 预期一致性。

### 1.4 HR —— 人事与架构负责人

- **定位**：管理**旗下集群人力**（agent 资源）与架构调整；在 agentic team 中即管理 agent 归属、skill 配置等结构问题。
- **职责**：角色/agent 归属管理、skill 与能力配置、架构调整的落地；**与 C..O 协商调度资源、节约成本**；**记录不同模型 / Agent Program / CLI 参数配置可能带来的时间成本与用工成本**（大小智能管理的成本台账，见 [03-intelligence.md](03-intelligence.md)）。
- **关键产出**：人员/角色清单、配置变更、资源调度方案、成本台账。
- **权限**：**具有管理权**——可调整组织结构、agent 归属与 skill 配置；与 C..O 协商资源调度。
- **红线**：**不能越权**——不做业务线决策（不代替 CPO/CTO/COO 做业务判断），不触碰产品/技术/运营的具体内容；**不直接对话 CEO**（与 C..O、AS 对话）。
- **协作方**：各 C..O、AS（不直接对话 CEO）。
- **衡量指标**：配置准确率、资源调度及时性、成本节约。

### 1.5 AS —— 行政 / 代行

- **定位**：**CEO（个人/自然人）的代行人**，主要职责是**推动工作进行、防止任务停摆**。
- **职责**：
  - 推动 CEO **明确命令**持续进行；
  - 管理目前在办任务、确认推进进度；
  - 整理信息、**定期向 CEO 汇报**；
  - 处理杂务、跨线督办。
- **关键产出**：推进状态、进度确认、汇报记录、事务处理。
- **权限**：**受限推动权**——只推动 CEO 已明确表示的事项。
- **红线**：**不具其它职权，不得越权**——CEO 未明确表示的事项不得擅自行动；不代替任何 C..O 做业务决策；升级/决策最终由 CEO 确认。
- **协作方**：CEO（汇报对象）、HR、各 C..O。
- **衡量指标**：推进及时性、任务停摆率、汇报按时率。

### 1.6 TC 技术中心细分角色（CTO 下属）

CTO 下属为各层执行单位，区分**专家角色**（规划/领域负责/审查/审批）与**普通执行角色**（实现/运维）。TC 技术中心是一个 **Squad**，负责人为**技术总监 / 技术主管**（总监/主管类角色，向 CTO 汇报）。

#### Squad 负责人

**技术总监 / 技术主管（Tech Director / Tech Lead）**
- **定位**：TC 技术中心的**最终负责人**（总监/主管类角色），即 squad 负责人；向 CTO 汇报。
- **职责**：统筹 TC 执行与交付、跨子角色协调、对技术线结果负责。
- **权限**：在技术线内调度子角色、把关关键交付。
- **红线**：不改写产品定义（属 CPO）；重大技术方向需 CTO 确认。
- **衡量指标**：技术线交付质量与及时性。

#### 技术规划

**Architect 架构师（专家）**
- **定位**：TC 的规划专家，负责**为技术实现划分界限**。
- **职责**：技术规划、架构设计、方案评审、划分技术边界。
- **权限**：定义技术方案与实现边界。
- **红线**：不直接写业务功能实现（由研发执行）；方案重大变更需 CTO 确认。
- **衡量指标**：方案落地质量、技术债增速。

#### 研发执行（统一研发 + 领域专家）

**研发（统一执行角色）**
- **定位**：前后端通用的**普通执行角色**（FSE/FE/BE 三拆合并）；复杂任务可能出问题。
- **职责**：按方案实现前后端功能。
- **权限**：在分配的任务范围内实现。
- **红线**：复杂/高风险任务不宜独自承担，需领域专家或质量审查把关。
- **衡量指标**：交付质量、缺陷率。

**前端专家（FE 领域专家）**
- **定位**：负责**前端 / UI / 页面展示**领域的专家角色。
- **职责**：前端方案与实现质量把关、前端领域技术决策。
- **权限**：在前端领域内定义实现标准、评审前端产出。
- **红线**：不改后端逻辑（属后端领域）；不越权到产品成色定义（属 CPO）。
- **衡量指标**：前端实现质量、UI 还原度。

**后端专家（BE 领域专家）**
- **定位**：负责**后端 / 数据处理 / API** 领域的专家角色。
- **职责**：后端方案与实现质量把关、后端领域技术决策。
- **权限**：在后端领域内定义实现标准、评审后端产出。
- **红线**：不改前端展示（属前端领域）；不越权到产品成色定义（属 CPO）。
- **衡量指标**：接口质量、服务稳定性。

#### 质量审查（专家，三视角经 skill 配置拆分）

**质量审查（Quality Review）**
- **定位**：从**三个审查视角**把关质量（不设独立岗位，三视角经不同 skill 配置拆分）。
  - **Code 视角**：从代码质量层面审查——看代码本身写得好不好（规范、可维护性）。
  - **Plan 视角**：从计划层面审查——看计划写得好不好（清晰、合理、可执行）。
  - **Testing 视角**：从测试层面审查——**找极端情况，看响应好不好**。
- **职责**：代码审查、计划/方案审查、测试用例设计（含极端情况）、执行测试与回归。
- **权限**：给出审查结论、测试门禁结论，可要求修改后合入。
- **红线**：不做业务决策；只做质量把关，不改功能实现。
- **衡量指标**：审查问题发现率、一次通过率、缺陷逃逸率、极端情况覆盖率。

**UI Reviewer / UX Reviewer（可选，界面要求高时补充）**
- UI：从**用户界面**提出审查（视觉/布局）。
- UX：从**用户体验**提出审查（交互/流程；对 CLI 也有明确要求）。
- 红线：不审代码逻辑。

#### 运维（普通执行）

**Operation Engineer（Ops）**
- **定位**：运维执行角色。
- **职责**：环境、CI/CD 自动化、本地部署、云端监控。
- **权限**：发布与运维操作。
- **红线**：不做业务实现；发布/变更需安全员审批。
- **衡量指标**：部署成功率、MTTR、可用性。

#### 安全审批（专家）

**安全员（Security / 审批）**
- **定位**：主要负责**审批**的安全角色。
- **职责**：对发布、变更、权限做安全审批。
- **权限**：审批权（关键变更一票把关）。
- **红线**：不越权到业务实现。
- **衡量指标**：审批及时性、安全事故数。

#### 算法（单独中心原则）

- **AE 算法工程师**：算法问题更难，与前后端协作过多容易造成**上下文危险**——应**单独设一个中心**（如 AC 算法中心），不与前后端混编。v2 记录原则，具体结构后续定义。

## 2. 边界矩阵

| 事项 | 决策人 | 备注 |
| --- | --- | --- |
| 产品成色/质量 | CPO | 其他人可建议，不可拍板 |
| 技术实现方案 | CTO | —— |
| 长期运营执行 | COO | —— |
| agent 归属 / skill 配置 | HR | 有管理权，不可越权到业务 |
| 推动工作 / 杂务 | AS | 代行个人职权，不可越权决策 |
| 跨线冲突 / 最终裁决 | 个人（自然人） | AS 代为推动，但不替代裁决 |

## 3. 升级机制

- 低层无法解决的冲突或阻塞，按职责升级：
  - 产品/技术/运营之间的冲突 → 先由相关 C..O 协商；
  - 协商不成 → 交 **AS** 推动协调；
  - 仍无法解决 → 升级至 **CEO（个人/自然人）** 最终确认。
- 红线触发（越权）→ 立即纠正并复盘，记录到迭代复盘（[docs/05-iteration.md](05-iteration.md)）。

## 4. 边界管理原则

1. **可以蠢，不能越权**：执行质量可以不足，但权限红线必须守住。
2. **代行有度**：AS/HR 代行个人职权，推动与管理可以，决策不可越界。
3. **一摊一主**：每条线只有一个 owner（CPO/CTO/COO），避免多头决策。
4. **越权即事故**：越权行为按事故处理，复盘根因并更新边界。
