# 02 边界管理（v2）

> 定义每个角色的权限边界、红线与升级机制。核心原则：**可以蠢，不能越权**。

## 1. 角色规格与边界

### 1.0 角色规格通则（模板 + 差异）

角色规格采用**模板 + 差异**写法：共享字段抽到通则，每角色只写特有部分。字段模板：

> **定位 / 职责 / 关键产出 / 权限（能做）/ 红线（不能做）/ 协作方 / 衡量指标**

**共享通则（BG 成员通用，以下角色不重复）**：
- **裁量权**：职责内拥有裁量权，范围来自对 CEO 意图的揣摩——辨别核心内容，避免意图被曲解或错误执行。
- **少动原则**：遵循"少动"，不越权行事。
- **模型适配**：了解下属职员擅长/不擅长、适合/不适合的模型，用于准确派发任务（**派发是 C..O 的职责；HR 只管 Agent / 模型配置**，见 [03-intelligence.md](03-intelligence.md)）。
- **汇报**：向 CEO直接汇报。
- **档位**：BG 成员为 **EVP 级**；TC 中心负责人为**总监/主管级**；其余 TC 细分角色为**职员级**（按 [01-org-structure.md](01-org-structure.md) §5 命名规则）。
- **隶属**：各角色隶属于所在 **BG**，向对应负责人负责（普通职员不适用——其上下文依托 issue / project / lead 的 @）。

### 1.1 CPO —— 产品负责人（Chief Production Officer）

- **定位**：兼 **PC 产品中心**所属；负责产品的**成色设计**。
- **职责**：产品方向与体验设计、需求定义、质量把关、产品验收。
- **关键产出**：产品定义、需求与验收标准、成色（质量）基准。
- **权限**：在产品中心内决定"做什么、做成什么样"。
- **红线**：不直接决定技术实现方案（属 CTO）；不做长期运营执行（属 COO）。
- **协作方**：CEO、CTO、COO、HR、AS。
- **衡量指标**：产品成色/质量、需求交付、用户反馈、与 CEO 预期一致性。

### 1.2 CTO —— 技术负责人（Chief Technology Officer）

- **定位**：兼 **TC 技术中心**所属；负责**如何实现**产品。
- **职责**：技术架构、研发实现、技术交付、稳定性。
- **关键产出**：技术方案、实现代码/系统、交付物。
- **权限**：在技术中心内决定"怎么做、用什么实现"。
- **红线**：不改写产品定义（属 CPO）；不接管运营执行（属 COO）。
- **协作方**：CEO、CPO、COO、HR、AS。
- **衡量指标**：实现质量、交付效率、系统稳定性、与 CEO 预期一致性。

### 1.3 COO —— 运营负责人（Chief Operations Officer）

- **定位**：兼 **OC 运营中心**所属；负责产品的**长期执行**。
- **职责**：运营执行、增长与留存、长期执行闭环。
- **关键产出**：运营方案、执行记录、运营数据。
- **权限**：在运营中心内决定"如何长期执行"。
- **红线**：不改写产品成色定义（属 CPO）；不重造技术实现（属 CTO）。
- **协作方**：CEO、CPO、CTO、HR、AS。
- **衡量指标**：运营指标（留存/增长/转化）、执行闭环完整性、与 CEO 预期一致性。

### 1.4 HR —— 人事与架构负责人

- **定位**：管理 **Agent / 模型参数等配置**与**组织构成**（架构，非执行）；管理 agent 归属、skill 配置等结构问题。**不派发任务**（派发是 C..O 的职责）。
- **职责**：Agent / skill / 模型配置管理、组织构成（架构）调整的落地；**与 C..O 协商调度资源、节约成本**；记录成本台账（模型 / Agent Program / CLI 配置的时间成本与用工成本，见 [03-intelligence.md](03-intelligence.md)）。
- **关键产出**：Agent / 配置清单、配置变更、资源调度方案、成本台账。
- **权限**：**管理权**——调整 Agent / skill / 模型配置与组织构成；与 C..O 协商资源调度。
- **红线**：不做业务线决策、不派发任务；不触碰产品/技术/运营的具体内容；**不直接对话 CEO**（与 C..O、AS 对话）。**人事变动（运行时 / Agent / Skill 的增删）须 CEO 批准。**
- **协作方**：各 C..O、AS（不直接对话 CEO）。
- **衡量指标**：配置准确率、资源调度及时性、成本节约、人事变动合规率。

### 1.5 AS —— 行政 / 代行

> **统一口径**：**CEO 属于 BG，是 BG 的实际掌舵人与最终决策者**；BG 名义 lead 是 **AS**（代行 CEO，CEO 可不在场）。

- **定位**：**CEO 的代理人 / BG 名义 lead**；推动工作进行、防止任务停摆；下设 **Assistant AS** 执行高频简单推动。
- **职责**：推动 CEO 明确命令、管理在办任务、确认推进进度；定期向 CEO 汇报（**日报 S0 / 周报 S0-S2**，见 §5）；S0 才紧急通知；汇总红线扫描结果并按级别处置。
- **关键产出**：推进状态、进度确认、汇报记录、事务处理。
- **权限**：**受限推动权**——只推动 CEO 已明确表示的事项。
- **红线**：CEO 未明确表示的事项不得擅自行动；不代替 C..O 做业务决策；升级/决策最终由 CEO 确认。
- **协作方**：CEO（汇报对象）、HR、各 C..O、Assistant AS。
- **衡量指标**：推进及时性、任务停摆率、汇报按时率、阻塞升级质量。

#### Assistant AS（AS 二级能力 / 助理）

- **定位**：AS 的**二级能力**（较便宜档，属 **Assist 档**），负责**高频、简单**的推动与扫描工作。**建议作为"触发/@ 器"使用**——成本最低，适合高频例行触发。
- **职责**：
  - **例行推动 + 红线 S0 扫描同频**，统一 **10min ~ 1h 一次**（由触发器统一把控时间，到点统一触发）；
  - 按**红线分级（S0/S1/S2）扫描**（见 §5 红线分级与检测机制）；
  - 遇阻塞先 **push**；push 不动 → **通知 AS**，并**告知严重性**；
  - 汇总高频状态，供 AS 决策。
- **权限**：仅做简单推动与状态采集；不决策。
- **红线**：遇无法推动的阻塞**不擅自处置**，必须上报 AS；不越权。
- **汇报对象**：AS（不是 CEO）。
- **衡量指标**：推动频率、阻塞发现及时性、上报严重性准确性。

### 1.6 CKO —— 首席知识官（Chief Knowledge Officer）

- **定位**：BG 直属成员，负责**知识管理**——管理 skills、获取最新资讯、管理 BG 内部文档（尤其是 issue）。
- **职责**：skills 库维护、资讯获取与沉淀、文档管理、**issue 关闭权限**（issue 的关闭由 CKO 执行，不在其他人）。
- **关键产出**：skills 库、资讯简报、文档库、issue 关闭记录。
- **权限**：管理 skills 与文档；**关闭 issue**。
- **红线**：不做业务线决策；不越权到产品/技术/运营内容。
- **协作方**：HR（skill 配置协同）、各 C..O、AS。
- **衡量指标**：skills 库完整度、文档及时性、issue 关闭规范率。

### 1.7 TC 技术中心细分角色（CTO 下属）

CTO 下属为各层执行单位，区分**高级岗（Senior，仅前端 / 后端）**与**普通角色**（实现 / 规划 / 审查）。**运维与安全审批不属于技术职能，分属运营中心（OC）——产品上线相关交由运营**。TC 技术中心是组织单元，负责人为**技术总监 / 技术主管**（总监/主管类角色，向 CTO 汇报）。

#### 中心负责人

**技术总监 / 技术主管（Tech Director / Tech Lead）**
- **定位**：TC 技术中心的**最终负责人**（总监/主管类角色），即中心负责人；向 CTO 汇报。
- **职责**：统筹 TC 执行与交付、跨子角色协调、对技术中心结果负责。
- **权限**：在技术中心内调度子角色、把关关键交付。
- **红线**：不改写产品定义（属 CPO）；重大技术方向需 CTO 确认。
- **衡量指标**：技术中心交付质量与及时性。

#### 技术规划

**Architect 架构师**
- **定位**：TC 的规划岗，负责**为技术实现划分界限**。
- **职责**：技术规划、架构设计、方案评审、划分技术边界。
- **权限**：定义技术方案与实现边界。
- **红线**：不直接写业务功能实现（由研发执行）；方案重大变更需 CTO 确认。
- **衡量指标**：方案落地质量、技术债增速。

#### 研发执行（统一研发 + 前端/后端 Senior）

**研发（统一执行角色）**
- **定位**：前后端通用的**普通执行角色**（FSE/FE/BE 三拆合并）；复杂任务可能出问题。
- **职责**：按方案实现前后端功能。
- **权限**：在分配的任务范围内实现。
- **红线**：复杂/高风险任务不宜独自承担，需前端/后端 Senior 或质量审查把关。
- **衡量指标**：交付质量、缺陷率。

**前端 Senior（FE 高级岗）**
- **定位**：负责**前端 / UI / 页面展示**领域的高级岗（Senior）。
- **职责**：前端方案与实现质量把关、前端领域技术决策。
- **权限**：在前端领域内定义实现标准、评审前端产出。
- **红线**：不改后端逻辑（属后端领域）；不越权到产品成色定义（属 CPO）。
- **衡量指标**：前端实现质量、UI 还原度。

**后端 Senior（BE 高级岗）**
- **定位**：负责**后端 / 数据处理 / API** 领域的高级岗（Senior）。
- **职责**：后端方案与实现质量把关、后端领域技术决策。
- **权限**：在后端领域内定义实现标准、评审后端产出。
- **红线**：不改前端展示（属前端领域）；不越权到产品成色定义（属 CPO）。
- **衡量指标**：接口质量、服务稳定性。

#### 质量审查（三视角经 skill 配置拆分）

**质量审查（Quality Review）**
- **定位**：从**三个审查视角**把关质量（不设独立岗位，三视角经不同 skill 配置拆分）。
  - **Code 视角**：从代码质量层面审查——看代码本身写得好不好（规范、可维护性）。
  - **Plan 视角**：从计划层面审查——看计划写得好不好（清晰、合理、可执行）。
  - **Testing 视角**：从测试层面审查——**找极端情况，看响应好不好**。
- **职责**：代码审查、计划/方案审查、测试用例设计（含极端情况）、执行测试与回归。
- **权限**：给出审查结论、测试门禁结论，可要求修改后合入。
- **红线**：不做业务决策；只做质量把关，不改功能实现。
- **衡量指标**：审查问题发现率、一次通过率、缺陷逃逸率、极端情况覆盖率。

**UI Reviewer / UX Reviewer（可选，界面要求高时补充）**
- UI：从**用户界面**提出审查（视觉/布局）。
- UX：从**用户体验**提出审查（交互/流程；对 CLI 也有明确要求）。
- 红线：不审代码逻辑。

#### 运维与安全审批（已移出 TC）

- **运维（Operation Engineer）与安全审批（安全员）不属于技术职能**，分属**运营中心（OC）**——环境 / 部署 / 监控、发布审批等**产品上线相关交由运营（COO）**负责；OC 细分角色待讨论。

#### 算法（单独中心原则）

- **AE 算法工程师**：算法问题更难，与前后端协作过多容易造成**上下文危险**——应**单独设一个中心**（如 AC 算法中心），不与前后端混编。v2 记录原则，具体结构后续定义。

## 2. 边界矩阵

| 事项 | 决策人 | 备注 |
| --- | --- | --- |
| 产品成色/质量 | CPO | 其他人可建议，不可拍板 |
| 技术实现方案 | CTO | —— |
| 长期运营执行 | COO | —— |
| agent 归属 / skill 配置 | HR | 有管理权，不可越权到业务 |
| 推动工作 / 杂务 | AS | 代行 CEO 职权，不可越权决策 |
| issue 关闭 | CKO | 关闭权限在 CKO，不在其他人 |
| 跨中心冲突 / 最终裁决 | CEO | AS 代为推动，但不替代裁决 |

## 3. 升级机制

- 低层无法解决的冲突或阻塞，按职责升级：
  - 各中心之间的冲突 → 先由相关 C..O 协商；
  - 协商不成 → 交 **AS** 推动协调；
  - 仍无法解决 → 升级至 **CEO** 最终确认。
- **CEO 未决策时的停摆处理**：升级至 CEO 后若 CEO 超时未决策，视为**项目停摆**——由 **AS 记录**停摆事项，在 AS **定期向 CEO 汇报**时**统一通知**，避免任务长期停摆。C..O 超时可凭职责内**裁量权先行处理**，但需**高层一致通过**（见下）并**上报 AS**；不越权到需要 CEO 拍板的高风险/不可逆事项。
- **高层会议（最高事项）**：BG 统一决策——专门开一个 **issue** 讨论；**全体一致通过**时视为无异议，可以**越过 CEO 裁决**，但仍保留向 CEO 汇报的义务。
- 红线触发（越权）→ 立即纠正并复盘，记录到迭代复盘（[docs/05-iteration.md](05-iteration.md)，**属 CKO 职责**）。

## 4. 边界管理原则

1. **可以蠢，不能越权**：执行质量可以不足，但权限红线必须守住。
2. **代行有度**：AS/HR 代行 CEO/管理职权，推动与管理可以，决策不可越界。
3. **一摊一主**：每个中心只有一个 owner（CPO/CTO/COO），避免多头决策。
4. **越权即事故**：越权行为按**红线分级（S0/S1/S2）检测、处置并复盘**（见 §5），复盘根因后更新边界。

## 5. 红线分级与检测机制

"可以蠢，不能越权"需要**可观测的检测信号**。红线判定与分级写入专门的**红线文档**；由 **Assistant AS**（或安全角色，成本最低，作为触发/@ 器）高频扫描、**AS** 低频复核；处置与汇报按级别分级。**红线文档在 Multica 中以 issue 形式存在**——若有外部链接则 issue 内保存链接，否则 issue 本身即文档。

### 5.1 什么算红线（判定口径）

**红线由红线手册（S0/S1/S2）确定**，关键在于**高风险**——不是执行者或探测者自己拍板。手册之外的可疑动作，按**升级三问**决定是否升级复核；由 **CKO 对照红线手册**认定级别（S0/S1/S2），不在手册的补充进手册。

升级三问（用于决定是否**升级复核**，不是直接定红线）：
1. **是否越权**：该行为是否在本角色权限之外（对照 §1 角色规格与 §2 边界矩阵）？
2. **是否影响他中心/整体**：该行为是否改变了其它中心的产出、成本或公司整体结果？
3. **是否不可逆/高风险**：错误执行是否会造成重大或难以挽回的损失？

任一指向"是" → **升级给 AS / CKO 复核**，由 CKO 对照红线手册认定级别；三问皆"否" → 属正常执行 / 职责判断，不升级。**不算红线**：能力不足导致的执行质量问题（"可以蠢"）、正常范围内的职责判断、明确标注可授权的事项。

### 5.2 红线分级（S0/S1/S2）

| 级别 | 类型 | 判定特征 | 示例（判定基准） |
| --- | --- | --- | --- |
| S0 | 重大事故 | 越权且影响非常大、几乎一定造成重大损失 | 越权发布/删除关键资产、篡改他中心核心决策、造成不可逆数据或资金损失 |
| S1 | 事故 | 越权有一定影响、相对隐蔽；及时改正可避免重大损失 | 未经授权变更他中心配置、越权调度的可逆影响、擅改对外承诺 |
| S2 | 风险 | 越权大多隐蔽、暂未造成实质损失但存在风险 | 权限边界模糊的越界动作、应上报未上报的决策、潜在越权倾向 |

> 分级判定以红线文档为准；实际运行中按发生频率与损失复盘调整（见 [docs/05-iteration.md](05-iteration.md)）。

### 5.3 扫描节奏（由触发器统一把控）

| 级别 | 扫描频率（初始建议值） | 处理者 |
| --- | --- | --- |
| S0 | **10min ~ 1h 一次**（与例行推动同频，触发器到点统一触发） | Assistant AS / 安全角色（低成本） |
| S1 | 1h ~ 2h 一次 | Assistant AS |
| S2 | 每日 / 每周 | AS 复核 |

> 频率为**可调参数**，按实际运行复盘调整，避免过度扫描造成成本与噪声失控。所有扫描、审计、报告工作注意**时间留痕**（何时触发、扫描结果、处置动作）。

### 5.4 处置与通知

- **S0 发生**：Assistant AS **紧急叫停**，并**紧急通知 CEO（个人）**；告警由 Autopilot 规则触发（不是人值班待命）。
- **S1 发生**：不需要叫停，但要做好**通知**；S1 影响扩大可能**上升 S0**，需引起警戒。
- **S2 发生**：不需要叫停、不需要通知，**做好汇报即可**。
- **正常停摆（下班）**：属正常阻塞，虽使工作停摆，但不作过分要求。

### 5.5 AS 汇报职责（对 CEO/个人）

- **日报**：主要记录 **S0 事件**——事件记录、持续时间、解决方案，**做好时间轴**。
- **周报**：**S0-S2 全部**汇总——事件、持续时间、发生时间、是否完成解决。
