# 03 协作流（v1）

> 本文档定义 agentic team 的核心协作流与升级机制，覆盖：需求 → 设计 → 技术 → 测试 → 发布，以及产品 / 技术 / 行政之间的协同。

## 1. 核心价值流：需求 → 设计 → 技术 → 测试 → 发布

```
需求 ──> 设计 ──> 技术 ──> 测试 ──> 发布 ──> 反馈
 │        │        │        │        │        │
PM/SPM   Designer   TL/团队   QAE     SRE/PM   数据/用户
+PRD     +设计稿    +实现     +门禁    +上线     回流需求池
```

| 阶段 | Owner | 参与方 | 关键动作 | 出口物 |
| --- | --- | --- | --- | --- |
| 需求 | PM / SPM | PD、APM、产品设计、TL | 需求分析、优先级评审 | PRD + 验收标准 |
| 设计 | 产品设计 | PM、FE、TL | 交互/视觉设计、评审 | 设计稿、原型 |
| 技术 | TL | 架构师、FE/BE/AE | 方案设计、任务拆解、实现 | 代码 + 技术方案 |
| 测试 | QAE | PM、TL、开发 | 用例设计、功能/回归/性能测试 | 测试报告 + 门禁结论 |
| 发布 | SRE | PM、QAE、TL | 部署、发布说明、监控 | 线上版本 + 发布说明 |
| 反馈 | PM | 运营(占位)、数据、用户 | 数据回收、用户反馈 | 反馈汇总 → 下轮需求 |

### 1.1 阶段间交接规则

- **需求→设计**：PRD 评审通过后，PM 将需求与验收标准交接给产品设计；设计稿需 PM 确认。
- **设计→技术**：设计稿评审通过后交给 TL；TL 与架构师（必要时）出技术方案，拆解任务。
- **技术→测试**：开发自测通过后提交 QAE；QAE 按验收标准出测试用例并执行。
- **测试→发布**：QAE 门禁通过（无阻塞缺陷）后，SRE 执行部署；PM 编写发布说明。
- **发布→反馈**：上线后由 PM 收集数据与用户反馈，回流到需求池，进入下一轮迭代。

### 1.2 每条流的原则

1. **同一需求有唯一 Owner**（PM）：跨阶段由 PM 全程跟进，避免"手递手"断链。
2. **出口物先行**：每个阶段先对齐出口物再开工，减少返工。
3. **门禁明确**：测试、发布阶段必须拿到明确门禁结论，不允许模糊通过。
4. **变更受控**：阶段中需求变更需走"变更登记"（见第 3 节），避免无序蔓延。

## 2. 产品 / 技术 / 行政协同

### 2.1 产品 × 技术

- **对齐场合**：迭代规划会（对齐范围）、评审会（对齐方案）、复盘会（对齐结果）。
- **日常接口**：PM ↔ TL 为默认接口人；复杂方案由架构师参与评审。
- **冲突处理**：优先级冲突由 PD 与 CTO 协商；协商不成升级 CEO。

### 2.2 产品 × 行政（HRD / HR）

- 新角色 / 新任务类型出现时，产品线提出需求，HRD 负责角色定义与绩效机制，HR 负责"补齐"（一人公司中即明确由哪个 agent 承担）。
- 绩效数据由 HR 汇总，供迭代复盘使用。

### 2.3 技术 × 行政

- 权限、账号、流程类需求走行政线；行政线的工具与流程建设需要技术支持时，向 TL 提需求。

## 3. 变更控制

| 变更类型 | 处理方式 |
| --- | --- |
| 需求变更（范围内调整） | PM 登记变更、评估影响（范围/时间/成本），TL 确认后执行 |
| 范围新增 / 删减 | PD 决策；影响跨中心时升级 CEO |
| 技术方案变更 | 架构师 / TL 评审后更新技术方案，同步 QAE 更新用例 |
| 角色/组织变更 | 走 [02-roles.md](02-roles.md) 第 7 节的角色变更流程 |

## 4. 升级机制

阻塞或冲突按如下层级逐级升级，**低层无法在时限内解决时立即升级，不积压**：

```
工程师 ──> TL ──> CTO（技术问题） / PD（产品问题） ──> CEO ──> 用户（自然人老板）
```

- **默认时限**：普通阻塞 24h 内升级；发布阻断级问题立即升级。
- **升级必备信息**：问题描述、影响范围、已尝试方案、需要的决策。
- **CEO 裁决**：跨中心无法达成一致的决策由 CEO 拍板，并记录决策理由。

## 5. 例行同步节奏

| 活动 | 频率 | 参与者 | 目的 |
| --- | --- | --- | --- |
| 迭代规划会 | 每迭代开始 | 各中心 | 对齐范围、优先级、分工 |
| 站会（轻量） | 每日 | 各执行角色 | 同步进度、暴露阻塞 |
| 评审会 | 每迭代中 | PM/TL/QAE | 评审关键交付物 |
| 迭代复盘会 | 每迭代结束 | 全员 | 复盘结果、沉淀改进项 |
| 周报/月报 | 周/月 | 各中心负责人 | 向上汇报、跨线透明 |

## 6. 质量与发布门禁

1. **测试门禁**：QAE 无 P0/P1 缺陷 → 允许发布；否则打回修复后复测。
2. **发布门禁**：SRE 确认部署成功、监控无异常 → 发布完成。
3. **上线后**：PM 跟踪关键指标与用户反馈，异常时触发回滚或热修复（SRE + 相关开发）。

> 具体迭代节奏、评审与复盘机制见 [04-iteration-plan.md](04-iteration-plan.md)。
