# 04 迭代机制（v1）

> 本文档定义团队如何持续迭代：迭代节奏、反馈闭环、架构版本演进。

## 1. 迭代节奏

- **默认节奏**：**双周迭代**（2 周 / 迭代）。可在 OPC 阶段视体量缩短为单周迭代，稳定后再拉长。
- **一个迭代周期**：
  - Day 1：迭代规划会（定范围、优先级、分工）；
  - Day 2~9：执行（按 [03-collaboration-flows.md](03-collaboration-flows.md) 的价值流推进）；
  - Day 10~11：测试与发布（含发布门禁）；
  - Day 12：迭代复盘会（结果复盘 + 改进项入库）。

## 2. 迭代四步循环：规划 → 执行 → 评审 → 复盘

```
     ┌──────────┐
     │   规划    │ 目标/范围/优先级/分工（迭代规划会）
     └────┬─────┘
          ▼
     ┌──────────┐
     │   执行    │ 需求→设计→技术→测试→发布
     └────┬─────┘
          ▼
     ┌──────────┐
     │   评审    │ 关键交付物评审（评审会）
     └────┬─────┘
          ▼
     ┌──────────┐
     │   复盘    │ 结果 vs 目标、过程改进项（复盘会）
     └────┬─────┘
          │  改进项 → 进入下一轮规划
          └──────────┐
                     ▼
                下一轮迭代
```

### 2.1 规划

- 输入：目标、需求池（含上轮回流）、技术债、角色能力现状。
- 输出：迭代范围、优先级排序、负责人（角色）分工、验收标准。
- 原则：每个迭代至少有一个可交付的用户可见结果（可用性优先）。

### 2.2 执行

- 按价值流推进，每阶段有明确 Owner 与出口物（见 [03-collaboration-flows.md](03-collaboration-flows.md)）。
- 每日站会同步进度、暴露阻塞；阻塞按升级机制处理。

### 2.3 评审

- 关键交付物（PRD、设计稿、技术方案、测试报告）按阶段评审。
- 评审结论需明确：通过 / 有条件通过 / 打回。

### 2.4 复盘

- 复盘两个维度：
  - **结果**：迭代目标达成率、交付质量、发布情况；
  - **过程**：协作效率、阻塞根因、角色职责是否清晰、流程是否顺畅。
- 产出：改进项清单（责任角色 + 截止时间），进入下一轮规划。

## 3. 反馈闭环

反馈回流是迭代改进的核心，覆盖 5 类信号：

| 反馈源 | 信号 | 收集方 | 处置 |
| --- | --- | --- | --- |
| 用户 | 用户反馈、投诉、满意度 | PM / 产品设计 | 进入需求池，按价值排序 |
| 数据 | 核心指标（留存/转化/性能） | PM / 数据运营(占位) | 判断产品假设，决定调整方向 |
| 缺陷 | 线上缺陷、回归失败 | QAE / SRE | 按严重级别修复，回流测试 |
| 内部协作 | 阻塞、重复劳动、沟通成本 | 各角色 | 复盘会沉淀改进项 |
| 技术债 | 维护成本上升、性能劣化 | 架构师 / TL | 进入技术债清单，排期偿还 |

闭环要求：每个信号都必须有**归口角色**与**下一步动作**，不允许只记录不处置。

## 4. 架构版本演进

### 4.1 版本规则

- 架构文档采用 `vX.Y` 版本号，记录在 `docs/` 各文档标题中。
- **v1**：当前版本，单一 BG（OPC），运营/市场/ BU 为占位。
- 版本变化规则：
  - **v1.x（小版本）**：角色职责微调、协作流细节补充、占位说明完善，不改变整体结构。
  - **v2（大版本）**：新增组织单元（如运营线展开、BU 正式化）、结构调整、多 BG 扩展。

### 4.2 演进流程

1. **提出**：在复盘会或评审会上提出架构变更建议（含动机与影响范围）。
2. **评审**：CEO 主持、各中心负责人参与，评估对角色/协作/迭代的影响。
3. **落地**：同步更新 `docs/01~04` 全部相关文档，并更新 README 中的架构总览。
4. **记录**：变更记录到本文件第 6 节"变更记录"。
5. **发布**：按云↔本地同步规则（见 README）提交并推送。

### 4.3 架构版本与产品版本的关系

- 产品/业务有自己的发布版本；架构版本独立演进，二者不强制同步。
- 一次架构大版本升级，建议选择产品节奏相对稳定的窗口进行。

## 5. 团队自身的迭代

- **角色与技能**：按 [02-roles.md](02-roles.md) 的角色变更流程调整；一人公司中"谁能兼任什么"是常态迭代对象。
- **流程**：复盘发现的低效环节优先改进（如简化评审、自动化测试/发布）。
- **文档**：任何角色、协作、迭代机制的变更，**必须同步更新本仓库对应文档**，保持架构文档始终为最新。
