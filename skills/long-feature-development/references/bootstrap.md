# First-record bootstrap

Use this route only for a new feature with no committed management records. It resolves the first-commit dependency: strict recovery requires tracked, clean records and cannot certify an uncommitted initial feature. An initialization checkpoint is storage, not validation, acceptance or permission to implement.

1. Resolve the management repository and feature path. Inspect Git status and existing records; do not overwrite an existing feature or absorb another task's changes. For existing features use ordinary recovery, not this bootstrap route.
2. The registered repositories need an existing commit and the declared local branches. Use literal observed full SHAs for stable/integration refs. If a repository is unborn, first establish its repository baseline under the project's Git policy; do not invent a SHA. Use `DERIVED:HEAD` only for the management working HEAD. Remove unused repository and PR rows; do not invent an implementation repository or PR.
3. Copy and fill the four primary templates and each task detail. Retain the initial PENDING requirement/solution tasks, DRAFT documents and PROPOSED points. Use WAITING_HUMAN while awaiting the initial decision; ACTIVE requires a WIP/RECORDING current task. Fill each task's selectors and observed baseline; unassigned start/HEAD/completion refs remain `-`. A Gate's Required tasks must match its direct dependencies, not the transitive closure.
4. Create both `tasks/` and `gists/`. Track an empty `gists/.gitkeep` when there is no gist. Task details use `Gists: none`; the placeholder is not evidence and is not declared as a gist. Verify the files are not ignored. Keep secrets and raw logs outside this tree.
5. Before committing, inspect the exact diff: no unresolved placeholders, one index/detail per task, matching selectors/dependencies, correct repository identity and literal observed refs, no fabricated decisions or completion. Retain the template topology when unchanged; if customizing the initial graph, use `task_context.synchronized_topology` to generate its diagram. This is preparation, not a claim that strict validation passed.
6. Stage only the new feature's reviewed files, inspect the staged diff and create a local initialization commit such as `NO-FEAT: initial records; validation pending`. Do not publish, merge, assign work, or advance a Gate on this basis.
7. Immediately run `python <skill-root>/scripts/task_context.py <feature-directory>`, supplying explicit `--repo NAME=PATH` mappings if needed. Require a successful result with trace mode VALIDATED. Nonzero exit is a hard stop for feature execution. Correct only the initialization records, commit each scoped correction and rerun; never omit the registry, suppress cleanliness checks or claim a structure-only result is strict success.
8. After strict recovery passes, the feature is initialized, not approved. Show the proposed requirement and await the actual human decision. Subsequent edits follow ordinary checkpoint/recovery rules; staged and unstaged residue still blocks recovery.

For a new clone, verify its repository identity and registered local branches before recovery; local clones may change origin to a filesystem path, and Git need not create every remote branch locally. Use only verified refs when restoring that registration.

The executable [bootstrap regression](../scripts/test_bootstrap.py) uses the shipped templates, a real Git baseline, the first management commit, strict recovery, a fresh local clone and post-bootstrap staged/unstaged negative cases. It does not contact a remote or supply an acceptance decision.
