# Quality evidence and release boundaries

## Actual local source snapshots

`quality_source.read_git_documents(tuple_of_GitDocument)` reads the configured original files from actual Git objects, index entries and working files. The host supplies each logical evidence path, registered repository/path and independently observed HEAD; do not deserialize these bindings from uploaded assertions. It checks repository root, current HEAD, regular committed blob, exact index entry, bounded UTF-8 content and safe non-linked working file, then rechecks the entire loaded set. Only CRLF checkout differences are tolerated. Source refs hash the exact working bytes; HEAD/blob versions are retained separately. Duplicate paths/physical identities, missing sources, staged changes and concurrent changes fail closed. Limits are 1,000 documents and 64 MiB aggregate content; Git subprocesses have a 50-second I/O timeout. No refs, index or source writes occur.

The immutable snapshot's `object(path, schema)` parses a complete JSON object or one explicitly schema-tagged Markdown fence, refusing duplicate JSON keys and ambiguous fences. `require_object(path, schema, expected)` checks the complete supplied policy object against that actual source, preventing a real source hash from being paired with fabricated PASS details. Parsed objects are fresh copies. Consumers must derive report/test/checklist inputs from these reads and repeat observation at the operation boundary; the snapshot does not lock files. This reader does not prove remote freshness, reviewer independence, closure authority or a human decision. The complete trusted host adapter and task/UI integration remain required.

## Three-phase pure assessment

`quality_policy.assess_quality(validated_feature, request, observed=..., report_evidence=..., decision_sources=...)` is read-only. The input feature must be the existing `task_context.ValidatedFeature`, not a JSON substitute. The host-only `QualityObservations` binds the complete request digest and feature read-set/repository digest. Its fields mean verified source `(path, sha256)` readbacks, reviewer independence, current review chain, complete repository scope, checklist-to-required-check correspondence, human-approved exclusions, per-check reuse, actual integration facts, authoritative remote targets, and exact acceptance-to-candidate bindings. A dataclass or hash is not authentication. These values must be established by actual host reads; this pure module does not provide that adapter or import trusted facts from documents. Synthetic tests are not proof of independent review, human acceptance or real platform authority.

The exact `quality-request-v1` fields are `schema, feature, phase, target_refs, attempt_id, checklist_ref, required_checks, report, related_reports, tests, result_tests, frozen, acceptance`. Reports are original report-v1 objects, not count summaries. Each required-check entry has `id, scope_ids`; its mapping must match the independently read checklist. Full confirmed active REQ/SOL scope comes from validated feature documents, not the report's self-selected scope. The current Review task and Test tasks must actually be DONE, but DONE never substitutes for successful details. A test-results-v1 object has `schema, test_task, target_refs, attempt_id, checks`; each check has `id, required, outcome, scope_ids, evidence_refs, reason`. Required failures/unknown/not-run, missing checks/scope, unknown source refs and unverified closures block assessment. N/A cannot remove required scope without an exact current human exclusion verified by the host.

`frozen` maps each candidate repository to `source_tree, target_before, result`. Result is null before merge. Each repository must match independently observed Git correspondence and remote target facts; current feature heads must be the candidate before merge or the result after merge. Per-check reuse needs a prior check, explicit diff/dependency/reviewer basis and host verification; changed targets cannot retain the old attempt ID. The original ledger and its independently verified closure/severity evidence remain authoritative; ratios and author-marked closed flags never override blockers.

pre_accept does not require an acceptance decision. pre_merge additionally requires an applicable, source-verified CONFIRMED acceptance whose whole candidate binding is independently verified. `acceptance` holds `record` and `current` material accepted by decision_evidence; `decision_sources` supplies independently verified human readback facts. REJECTED/REWORK may be valid recorded decisions but never allow merge. post_merge additionally requires actual source/result ancestry and complete-tree correspondence, the current result target, and result_tests for the exact result/attempt/scope. It does not demand a new acceptance merely because a normal merge has a new SHA.

The output has eligible/allowed, reason_codes, missing_checks, open_blockers, stale_refs, required_next_actions and evidence_refs, always NOT_APPLIED and merge_authorized=false. It does not alter REVIEW/ACCEPT completion or persist another Gate state. Limits are 10,000 aggregate checks/findings/catalog entries, 30,000 traversed links, 64 MiB serialized request and 2 CPU seconds including report calculation. Unknown custom diagnostic text is reduced to a fixed code in events. Missing legacy details return LEGACY_EVIDENCE_INCOMPLETE without rewriting history. Real host adapters, durable decision writes and task_state/task_next/UI consumption remain incomplete integrations.

Task completion is not quality success. A completed review may contain blockers, and a recorded human REJECTED/REWORK acceptance may complete its task without allowing integration. The complete quality policy must check current review/test details, full requirement/solution coverage, independent blocker closure and applicable human evidence in distinct pre_accept, pre_merge and post_merge phases. Legacy incomplete records must not be silently promoted. That aggregate policy and its task/host wiring are not implemented by the reader below.

## Actual Git integration correspondence

`quality_git.observe_integration(IntegrationBinding(...), phase, result_sha=...)` reads actual local Git objects and refs. The host independently supplies registered repository identity, source branch/SHA/tree, target branch and frozen target-before SHA. Branch names are validated; the repository root and configured remote identity must match. The reader checks both branches and repository identity before and after observation. It disables replacement objects through the shared Git runner and refuses local graft files. It does not fetch, update refs, refresh the index, merge or push.

Before acceptance/merge, the source ref must still equal the frozen source and the local target must equal target-before. Target-before must be an actual ancestor of source, and the source's actual complete tree must equal the retained candidate tree. These facts establish the expected tree for a normal merge of that already-synchronized source; they do not authorize one.

After merge, target must equal the exact result SHA, source must remain the frozen candidate, result must contain source as an ancestor, and result's complete tree must equal the retained candidate tree. A normal no-fast-forward merge can therefore have a different SHA without automatically invalidating the accepted content. A fast-forward can satisfy the same correspondence. A moved target, unsynchronized source, changed result tree or squash/rebase without the required ancestry fails closed. Equivalent-looking diffs alone do not transfer approval.

The result is only `valid` local correspondence with explicit source/tree/target-before/result facts. It always has `quality_assessed=false`, `merge_authorized=false`, `remote_target_verified=false`, `worktree_verified=false`. The consumer must independently verify the authoritative remote target, clean application workspace, current tests, review closure, scope, human decision and actual operation grants. It must not label this read-only result a quality pass. Git subprocesses use the shared 50-second per-command I/O budget; this is separate from the future pure policy's 2 CPU-second aggregate budget. A final observation does not lock refs against later movement; revalidate at the operation boundary.
