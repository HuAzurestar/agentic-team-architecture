# Quality evidence and release boundaries

The shared strict recovery reader rejects `assume-unchanged` and `skip-worktree` index entries with HIDDEN_INDEX_STATE before trusting a clean status. This covers the selected feature in its management repository and the full implementation/support repositories; unrelated management features remain outside scope. It reads bounded NUL-delimited index tags without refreshing the index or clearing flags. A hidden edit cannot become confirmed intent merely because ordinary Git status omits it. Inspect and resolve the flag and contents explicitly before resuming; the reader never overwrites that work.

## Actual host composition

### Read-only command-line diagnosis

Run `python scripts/quality_host.py <feature-directory> --config <bindings.json> --repo app=<actual-path> --format json` (omit `--format` for text). Text shows eligibility, reason codes, missing checks, blockers, stale/evidence refs and next checks, explicitly NOT_APPLIED with no merge grant. JSON contains the same assessment. Exit codes: 0 eligible, 1 policy denied after valid source reads, 2 invalid configuration/context/source. stderr emits only a `quality.evaluate` event with phase, allowed, reason codes, target vector and elapsed milliseconds, never original bodies or credentials.

The explicit configuration is bounded to 4 MiB and uses `quality-host-config-v1`, with exactly `schema, roles, documents, repositories`. `roles` contains `request, report, tests, checklist, related_reports` (array), and `result_tests` (path or null). Each document has `logical_path, repository` (registered name), `relative_path`; physical repository roots and HEADs are freshly resolved by the strict reader, not supplied by this JSON. Each repository binding contains `repository_ref, remote, expected_remote, source_branch, source_sha, source_tree, target_branch, target_before`; source/frozen refs must be independently retained candidates and are checked against actual Git. These are source-selection inputs, not proof of scope authorization or identity. Duplicate keys, unsupported fields (including allowed/provenance/module names), links, oversized data and configuration changes during observation are rejected without overwriting the file.

Standalone CLI has no authenticated reviewer/human transport and therefore cannot turn complete originals into verified independence or acceptance. It reports that missing provenance honestly. An actual Python host may embed `main(argv, read_provenance=its_authenticated_reader)`; there is no command-line trust switch or imported executable module. The full same source/policy checks run in both cases. Prepared-state mutation adapters, actual platform reader deployment, per-point decision commits and UI integration remain required separately.

`quality_host.evaluate(root, documents=..., roles=..., repositories=..., read_provenance=..., repo_overrides=...)` runs the actual strict local Feature reader, then the committed Git document and live delivery readers below. It consumes a whole quality-request-v1 original; the report and each related report, test and result-test object must exactly equal their separately read original and the task's declared Result gist. Registered source repository HEADs and physical declared paths must match. A real source hash cannot stand in for a different PASS object or an identical copy at another path. A structured checklist original uses `quality-checklist-v1` with exactly `schema, required_checks`; the required-check mapping and the request's checklist path/hash must match that original. Existing prose is not silently converted into a verified checklist.

SourceRoles and repository/document bindings are independently selected host configuration, not permissions deserialized from project files. The authenticated `read_provenance` callback receives immutable complete request/source bytes and versions bound to the feature and actual delivery observations. It must independently verify reviewer context/identity, current review chain, closure/severity evidence, exclusions/reuse and human decision/candidate applicability before returning HostProvenance for that exact digest. The type or digest itself is not authentication; no JSON allowed flag or dynamic plugin is accepted. With no callback, source reads may succeed but policy still denies unverified independence. Callback errors are redacted.

The host recomputes policy and re-reads provenance, complete originals, strict feature and actual delivery before returning an Assessment. `Assessment.for_task(current_source_ref, task_id)` supplies the existing QualityInputs consumed by selector/state guards, which compare the exact plan and recompute policy again. Do not cache an assessment across an operation boundary. No merge, publication, task mutation or persistent second Gate occurs. This entry requires clean committed metadata; a prepared state transition needs its own explicitly reconciled host reader, not a flag to ignore dirty state. Actual authenticated platform bindings, prepared-write composition, production workflow/UI callers and per-point decision commits remain separate unfinished integrations. The real-Git tests prove source and pipeline behavior; their identity callbacks are expressly synthetic.

## State-write integration

`task_state.update(root, args, evidence_reader=host_reader)` now guards new Acceptance WIP with pre_accept and final DONE Gate WIP/RECORDING/DONE with post_merge. Acceptance RECORDING with a real decision, and DONE, use a separate actual `decision_host.inspect_decision` path; CONFIRMED, REJECTED and REWORK can all be recorded when applicable. REVIEW completion and waiting Acceptance RECORDING do not require zero blockers. Missing legacy provenance fails a new write without rewriting historical records. The ordinary CLI has no evidence-import flag and therefore cannot perform these protected writes without the configured Python host reader.

The reader receives an immutable TransitionRequest binding resolved root, task, source/target state, complete before/after index digests and the bounded actual feature file read-set. It must independently reconcile prepared metadata and freshly read actual repository/remote, review and human facts, returning a TransitionEvidence bound to request.digest. QualityInputs uses that same binding and exact task; the writer checks plan identity, actual requirement/solution hashes and recomputes the correct policy. This callback is trusted host configuration, never loaded from project files; types or hashes are not authentication. A complete platform adapter is still required.

HumanDecisionInputs supplies the original record and configured current/reply/interpretation readers and grant. The writer requires the declared actual six-section brief to equal the approved/current body and its unique top-level Target version to equal the task Target SHA; actor, feature, kind and outcome must match. Decision provenance is re-read by the existing human gateway. The state writer invokes its host reader twice, including just before replacement, and rechecks source membership/hashes. Changed inputs preserve external edits and stop replacement; failed late checks remove only the writer's own temporary file. This is optimistic checking under the existing single coordinator, not an OS access-control boundary or an atomic cross-file/remote transaction. Merge/publish execution and per-point decision commits remain separate operations.

## Next-action integration

`task_next.GateEvidence.quality_inputs` carries host-only `QualityInputs(source_ref, task_id, feature, request, observations, report_evidence, decision_sources)`. The selector recomputes `assess_quality` before suggesting accept (pre_accept), merge/publish (pre_merge) or a final DONE Gate (post_merge). It checks the exact selection binding/task, complete normalized task graph/contracts and phase. A ready summary, serialized allowed flag, different plan or old observations cannot replace the policy. Missing historical details produce LEGACY_EVIDENCE_INCOMPLETE without rewriting any DONE record. The CLI's host JSON intentionally cannot import QualityInputs; authenticated host composition must use the Python API, not manufacture verified facts from stdin.

Operation capabilities and existing direct contradictions still apply. Successful policy grants no merge/publish authority. Normal post-merge correspondence is assessed against the accepted source vector plus actual result, so a different normal merge SHA alone does not demand another decision. Work, rework/retest/rereview and non-final Gates do not acquire a zero-blocker restriction. Selection only suggests actions; the separate state-write integration above validates protected task_state transitions. Neither module performs per-point decision commits or merge/publish. See the [composition tests](../scripts/test_quality_selection.py); their host provenance is synthetic, not an actual independent review.

## Actual local source snapshots

`quality_source.read_git_documents(tuple_of_GitDocument)` reads the configured original files from actual Git objects, index entries and working files. The host supplies each logical evidence path, registered repository/path and independently observed HEAD; do not deserialize these bindings from uploaded assertions. It checks repository root, current HEAD, regular committed blob, exact index entry, bounded UTF-8 content and safe non-linked working file, then rechecks the entire loaded set. Only CRLF checkout differences are tolerated. Source refs hash the exact working bytes; HEAD/blob versions are retained separately. Duplicate paths/physical identities, missing sources, staged changes and concurrent changes fail closed. Limits are 1,000 documents and 64 MiB aggregate content; Git subprocesses have a 50-second I/O timeout. No refs, index or source writes occur.

The immutable snapshot's `object(path, schema)` parses a complete JSON object or one explicitly schema-tagged Markdown fence, refusing duplicate JSON keys and ambiguous fences. `require_object(path, schema, expected)` checks the complete supplied policy object against that actual source, preventing a real source hash from being paired with fabricated PASS details. Parsed objects are fresh copies. Consumers must derive report/test/checklist inputs from these reads and repeat observation at the operation boundary; the snapshot does not lock files. This reader does not prove remote freshness, reviewer independence, closure authority or a human decision. The complete trusted host adapter and task/UI integration remain required.

## Three-phase pure assessment

`quality_policy.assess_quality(validated_feature, request, observed=..., report_evidence=..., decision_sources=...)` is read-only. The input feature must be the existing `task_context.ValidatedFeature`, not a JSON substitute. The host-only `QualityObservations` binds the complete request digest and feature read-set/repository digest. Its fields mean verified source `(path, sha256)` readbacks, reviewer independence, current review chain, complete repository scope, checklist-to-required-check correspondence, human-approved exclusions, per-check reuse, actual integration facts, authoritative remote targets, and exact acceptance-to-candidate bindings. A dataclass or hash is not authentication. These values must be established by actual host reads; this pure module does not provide that adapter or import trusted facts from documents. Synthetic tests are not proof of independent review, human acceptance or real platform authority.

The exact `quality-request-v1` fields are `schema, feature, phase, target_refs, attempt_id, checklist_ref, required_checks, report, related_reports, tests, result_tests, frozen, acceptance`. Reports are original report-v1 objects, not count summaries. Each required-check entry has `id, scope_ids`; its mapping must match the independently read checklist. Full confirmed active REQ/SOL scope comes from validated feature documents, not the report's self-selected scope. The current Review task and Test tasks must actually be DONE, but DONE never substitutes for successful details. A test-results-v1 object has `schema, test_task, target_refs, attempt_id, checks`; each check has `id, required, outcome, scope_ids, evidence_refs, reason`. Required failures/unknown/not-run, missing checks/scope, unknown source refs and unverified closures block assessment. N/A cannot remove required scope without an exact current human exclusion verified by the host.

`frozen` maps each candidate repository to `source_tree, target_before, result`. Result is null before merge. Each repository must match independently observed Git correspondence and remote target facts; current feature heads must be the candidate before merge or the result after merge. Per-check reuse needs a prior check, explicit diff/dependency/reviewer basis and host verification; changed targets cannot retain the old attempt ID. The original ledger and its independently verified closure/severity evidence remain authoritative; ratios and author-marked closed flags never override blockers.

pre_accept does not require an acceptance decision. pre_merge additionally requires an applicable, source-verified CONFIRMED acceptance whose whole candidate binding is independently verified. `acceptance` holds `record` and `current` material accepted by decision_evidence; `decision_sources` supplies independently verified human readback facts. REJECTED/REWORK may be valid recorded decisions but never allow merge. post_merge additionally requires actual source/result ancestry and complete-tree correspondence, the current result target, and result_tests for the exact result/attempt/scope. It does not demand a new acceptance merely because a normal merge has a new SHA.

The output has eligible/allowed, reason_codes, missing_checks, open_blockers, stale_refs, required_next_actions and evidence_refs, always NOT_APPLIED and merge_authorized=false. It does not alter REVIEW/ACCEPT completion or persist another Gate state. Limits are 10,000 aggregate checks/findings/catalog entries, 30,000 traversed links, 64 MiB serialized request and 2 CPU seconds including report calculation. Unknown custom diagnostic text is reduced to a fixed code in events. Missing legacy details return LEGACY_EVIDENCE_INCOMPLETE without rewriting history. Real host adapters, durable decision writes and task_state/task_next/UI consumption remain incomplete integrations.

Task completion is not quality success. A completed review may contain blockers, and a recorded human REJECTED/REWORK acceptance may complete its task without allowing integration. The complete quality policy must check current review/test details, full requirement/solution coverage, independent blocker closure and applicable human evidence in distinct pre_accept, pre_merge and post_merge phases. Legacy incomplete records must not be silently promoted. That aggregate policy and its task/host wiring are not implemented by the reader below.

## Actual Git integration correspondence

`quality_git.observe_delivery(binding, phase, result_sha=...)` composes the correspondence reader below with actual remote-target and clean-workspace observations. Before acceptance/merge the candidate branch must be checked out; after merge the result target branch must be checked out and published. It uses live `ls-remote`, not stale remote-tracking refs, and repeats observations around the local checks. Missing/unreachable/moved remote targets, detached/wrong checkout, untracked/staged/unstaged changes, assume-unchanged/skip-worktree entries and unfinished Git operations refuse delivery. Status respects checkout configuration (including CRLF) without index refresh; no fetch, merge or push occurs. Successful output adds actual working branch/head/remote target with `remote_target_verified=true` and `worktree_verified=true`, but still grants no quality success or merge authority. These are optimistic readbacks, not locks or proof of reviewer/human provenance; the full quality host must consume them and re-read at the operation boundary.

`quality_git.observe_integration(IntegrationBinding(...), phase, result_sha=...)` reads actual local Git objects and refs. The host independently supplies registered repository identity, source branch/SHA/tree, target branch and frozen target-before SHA. Branch names are validated; the repository root and configured remote identity must match. The reader checks both branches and repository identity before and after observation. It disables replacement objects through the shared Git runner and refuses local graft files. It does not fetch, update refs, refresh the index, merge or push.

Before acceptance/merge, the source ref must still equal the frozen source and the local target must equal target-before. Target-before must be an actual ancestor of source, and the source's actual complete tree must equal the retained candidate tree. These facts establish the expected tree for a normal merge of that already-synchronized source; they do not authorize one.

After merge, target must equal the exact result SHA, source must remain the frozen candidate, result must contain source as an ancestor, and result's complete tree must equal the retained candidate tree. A normal no-fast-forward merge can therefore have a different SHA without automatically invalidating the accepted content. A fast-forward can satisfy the same correspondence. A moved target, unsynchronized source, changed result tree or squash/rebase without the required ancestry fails closed. Equivalent-looking diffs alone do not transfer approval.

The result is only `valid` local correspondence with explicit source/tree/target-before/result facts. It always has `quality_assessed=false`, `merge_authorized=false`, `remote_target_verified=false`, `worktree_verified=false`. The consumer must independently verify the authoritative remote target, clean application workspace, current tests, review closure, scope, human decision and actual operation grants. It must not label this read-only result a quality pass. Git subprocesses use the shared 50-second per-command I/O budget; this is separate from the future pure policy's 2 CPU-second aggregate budget. A final observation does not lock refs against later movement; revalidate at the operation boundary.
