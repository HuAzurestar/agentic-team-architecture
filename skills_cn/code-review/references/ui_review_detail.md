# 弱审：UI

信息设计与真实任务操作一起审；代码本身不能证明体验。

## 信息

- 信息是否足够决策操作，是否解释过多、滚动过多、无意义空白或控件拥挤？
- 关键字段、主要操作和列表密度是否合理，是否必须横向寻找？
- 是否暴露 UUID、内部枚举、缩写和技术机制，文案是否属于用户语言？
- 按钮是否说明动作，无文字图标、省略号、加/叉/箭头和颜色是否有歧义？
- 状态是否只靠颜色，项目支持的输入方式能否使用焦点、交互和错误提示？
- 操作是否靠近对象，次要控件是否遮挡主要任务？

## 操作

- 写出从进入到完成任务的每一步，统计重复操作。
- 100 条记录是否批量处理，还是逐项选择、手填内部 ID？
- 可推导信息是否自动取得，默认值和确认步骤是否合理？
- 搜索/筛选/排序是否帮到任务，是否逼用户记住上一页信息？
- loading/progress、成功、部分成功和失败反馈是否明确？
- 能否原地恢复、保留输入/导航状态、避免重复提交？
- 已明确的 UI 验收范围是否完整交付，而非只证明按钮存在？

按实际列表规模操作默认、批量及失败恢复路径，记录动作序列和界面证据。尝试双击、中断、返回及批量内单项失败，追踪 UI→API→结果状态。无法操作时明确未知，不编造观察。
