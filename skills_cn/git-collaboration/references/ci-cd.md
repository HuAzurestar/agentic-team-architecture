# CI/CD 规范

GitHub 仓库在选定下述语言门禁后，还必须应用 [github.md](github.md) 中具体的工作流与平台能力映射。

## CI 拓扑

使用稳定、描述清晰的 job/check 名称。实用的拆分方式是：

- `policy`：PR 标题、禁止文件、生成文件一致性或仓库特定规则；
- `python`：适用时运行 lint/format、类型检查、测试和包构建；
- `cpp`：适用时运行格式、编译/静态分析、测试/sanitizer 和打包；
- `java`：编译/风格/静态分析、测试和包 smoke test；
- `shell`：语法/静态/格式检查和脚本测试；
- `lean`：使用固定工具链构建，并运行项目 linter/测试；
- `tex`：静态检查和文档构建；
- `integration`：只有存在跨组件行为时才添加。

在 Pull Request 和推送稳定分支时运行相关门禁。只有被跳过的 job 不会导致必需检查状态含糊时才使用路径过滤；共享 CI/构建配置发生变化时，必须触发受影响的 job。取消同一 PR 中已被新提交取代的运行。必需门禁应具有确定性并保持合理速度。

可用时使用平台支持的工具验证工作流语法。在威胁模型要求时，将第三方 Action 固定到可信不可变 revision，并通过自动更新工具维护固定版本。设置明确的 job 超时和最小权限。

根据实际交付物而非仅根据实现语言选择构建和打包门禁：

- 解释型脚本可能需要语法、导入、lint 和测试，但不需要包制品；
- 库应构建并验证使用者实际安装的包；
- 编译型应用应在 CI 中完成编译/链接，并测试生成的二进制文件；
- 可部署服务应只构建一次真实容器或 bundle，并测试该制品；
- 形式化证明应构建全部宣称定理模块，并审计未完成证明和信任假设；
- 论文应构建 PDF 并检查引用，按需生成预览或发布包。

行为逻辑至少应有单元测试。只有真实边界或支持承诺需要时，才增加集成、端到端或平台矩阵 job。构建成功不能替代测试；从不构建或导入实际交付制品的测试也不充分。

## 多语言仓库

检测仓库中的每种语言和交付物，不能只选择主语言。为每种适用语言提供独立的必需 job，使失败归因清晰（`python`、`cpp`、`java`、`shell`、`lean`、`tex` 等）。当输出跨语言边界时增加 `integration` job，例如 Python 生成 Lean/TeX 源文件、论文引用 Lean 结果、Java 调用原生库、Shell 打包制品，或 Python 导入 C/C++ 扩展。

增加名称稳定的最终聚合 job（例如 `ci / required`），让它依赖全部必需语言和集成 job；任何依赖失败或意外跳过时都失败。当单个矩阵名称或项目组成可能变化时，分支保护要求这个稳定聚合检查。只有轻量 change classifier 仍能给出明确成功/失败结果时才使用路径过滤；共享 manifest、生成器、workflow、schema 和锁文件必须触发所有受影响语言。

检测到的语言没有专用 reference 时，从仓库自己的 manifest、锁文件、贡献文档和现有 CI 推导门禁。在设计中记录组件、权威命令、制品和支持状态。证据不足时标记为不支持或未验证；不得静默遗漏组件，也不得默认引入流行工具链。

多语言 CD 使用统一 release manifest，记录源 commit/tag、工具链版本、校验和及所有预期 artifact。每种制品在所属且经过验证的 job 中构建，将不可变 artifact 交给汇总/release job；验证 manifest 完整后，以一个连贯版本共同发布。任何语言版本、二进制、证明 bundle、包或 PDF 失败时，都不能静默发布残缺 Release。

## Agent 辅助检查

部分 Git 平台提供 AI code review 或 Agent workflow；能力、许可、信任边界和 Fork 行为各不相同。Agent 可用于建议性代码审查、定理/引理搜索、测试缺口建议或维护任务。编译器、kernel、linter、测试和安全扫描等确定性检查仍应作为必需合并门禁。不得仅为审查不受信任的 PR 而授予 Agent 写权限或密钥。如果将 Agent 检查设为必需门禁，应尽可能固定其配置/模型，定义超时和失败语义，控制成本，并记录服务商中断时维护者如何处理。

## Release artifact profiles

每个发布交付物只能选择一种 profile，并记录在规范中：

1. **在 release ref 上构建一次：**受保护 tag 或显式 release workflow 检出已经验证的源 ref，只构建和测试一次发布制品，随后发布或晋级同一制品。
2. **晋级已经证明的候选制品：**CI 只构建测试一次候选制品，记录 digest、源 SHA、工具链、checks 和 provenance；release workflow 验证 tag/source 一致后原样晋级，不重新构建。

两种 profile 都保证验证与发布之间不会替换成未经测试的制品。后续添加打包元数据或签名时，如果会改变 payload 比特，就必须重新验证。适用时要求生产环境批准、串行执行生产部署，并记录制品版本、digest、源 commit、操作者和结果。

启用自动生产部署前先定义回滚方式。将凭证保存在代码托管平台或环境的密钥存储中，优先使用短期联合身份，绝不打印密钥。不得为不受信任的 Pull Request 运行带密钥的部署任务。

如果仓库是库、论文或形式化证明项目，没有运行时环境，那么“CD”可以合理地表示发布包、附加 PDF、创建 Release，也可以完全省略。不得只为凑齐缩写而虚构部署阶段。

## 采用顺序

在格式化现有基线或将检查限制于变更文件后，再引入格式和 lint 门禁。遗留类型错误存在时，应渐进引入类型检查。只有检查名称和触发行为稳定后，才将其设为分支保护必需检查。记录无法存入版本库、必须在托管平台中设置的配置。
