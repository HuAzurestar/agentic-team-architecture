# Lean 检查

将 `lakefile.lean` 或 `lakefile.toml`、`lean-toolchain` 和 `lake-manifest.json` 视为事实来源。使用固定的 Lean 工具链和已提交 manifest 保证可复现性。

基准门禁：

1. 使用项目的 Lake 流程获取依赖。只有有意更新 manifest 时才运行 `lake update`；配置 Mathlib 缓存时，普通构建优先使用 `lake exe cache get`。
2. 构建全部声明目标：`lake build`。
3. 不允许未完成证明。使用项目级检查拒绝依赖 `sorryAx` 的声明；只有警告策略受控且现有代码干净时，才可以通过“将 Lean 的 sorry 警告升级为错误”实现。文本搜索 `sorry` 只能作为补充性的快速检查，因为它可能漏掉别名/宏，也可能误中注释和示例。
4. 使用 `#print axioms <name>` 或等价的环境级审计检查公开定理或宣称的主要定理。拒绝 `sorryAx` 和未声明的项目公理。明确规定允许的公理集合；普通 Mathlib 证明通常应为 `propext`、`Classical.choice`、`Quot.sound` 的子集，但使用可信计算或领域公理的项目需要经过审查并记录自己的策略。
5. 确保包含宣称定理的模块被某个构建目标导入。未参与构建的文件即便包含合法定理，也不能算作经过验证的项目结果。
6. 只有项目定义了有效测试驱动器时才运行 `lake test`。
7. 存在时运行项目声明的 linter、可执行程序或汇总 `#lint` 的目标。

`lake build` 期间的 Lean elaboration 是主要语法和类型正确性门禁。不得虚构独立语法检查器。警告应得到处理或有意配置；现有代码库尚未清理干净前，避免在全局把所有警告升级为错误。

通过这些门禁，只能说明 Lean 在经过审计的信任假设下接受了已编译声明；它不能证明定理陈述忠实形式化了非形式化数学主张。重要结果仍须人工审查陈述定义、量词、假设、导入公理，以及论文/规格与 Lean 名称之间的映射。

## 可选 Agent 辅助审查

Git 平台和预算支持时，Agent 可以搜索已有引理、尝试独立重建证明、发现可疑的过弱陈述、审查新增公理/导入，或评价证明可维护性。默认将其作为建议性检查：Agent 成功不等于证明，Agent 失败不等于反证；除非团队已经测量并接受其可靠性、成本、权限和数据暴露，否则非确定性 Agent 输出不得代替 kernel 检查，也不应成为必需状态检查。

只有当缓存键包含操作系统、`lean-toolchain` 和 `lake-manifest.json` 时，才缓存 `.lake` 或 Mathlib 制品。普通 CI 验证任务绝不能以副作用形式重新生成或更新依赖 manifest。
