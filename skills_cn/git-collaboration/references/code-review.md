# 代码评审契约

本契约用于只读评估及 Pull Request/代码评审。编译器、kernel、linter、测试和安全扫描器等确定性证据仍是独立合并依据；人工或 AI 评审不能替代它们。

## 确定范围与覆盖率

评审前记录 base/head ref、变更文件、generated/vendor 排除项、检测到的语言、交付物及跨组件边界。审查每个范围内变更文件，或列出跳过理由。单看 diff 无法判断时，继续检查相关调用点、测试、schema、manifest、生成源文件和公共接口。

多语言变更先应用下述通用审查，再应用 `SKILL.md` 路由的每种语言 reference。明确审查以下边界：FFI/ABI、RPC/API schema、序列化、共享数据库、生成代码、包元数据、CLI 契约、版本字符串、证明与论文链接，以及制品汇总。

## 评审维度

- 正确性和边界情况，包括失败与并发行为；
- 安全、隐私、授权、密钥和不受信任输入；
- 兼容性、迁移、公共 API/ABI/schema 和支持版本影响；
- 能检测所声明行为的测试与可观测性；
- 可维护性、所有权、文档和生成源一致性；
- 构建、打包、发布、部署和回滚后果。

严重级别按后果确定，不能按风格偏好确定：

| Severity | 含义 |
| --- | --- |
| `blocking` | 不安全、错误、数据丢失、安全敏感或破坏发布的行为，合并前必须解决。 |
| `high` | 常见路径会失败，或承诺的兼容性/可靠性没有满足。 |
| `medium` | 有具体未来成本、范围有限的可维护性、测试或操作缺口。 |
| `advisory` | 可选改进或问题；绝不能表述为合并阻断项。 |

每个 finding 包含路径/行、可观察证据、后果、严重级别及聚焦的修复或验证步骤。区分事实与推断；测试没有实际运行时不得声称通过。没有可操作 finding 时，应说明已审查与跳过范围，不能虚构评论。

## 评审输出

按顺序返回：

1. blocking/high findings；
2. medium findings 与 advisory notes；
3. 覆盖率：已审查文件/组件/语言及跳过范围；
4. 验证证据：已经观察的命令/结果与仍需执行的检查；
5. 需要 owner 确认的跨语言或发布风险。

AI 辅助评审默认只作建议。像其他第三方 CI 依赖一样固定其版本和权限，不让不受信任变更接触密钥，定义超时/中断行为；绝不能把模型输出作为确定性正确性的唯一必需门禁。
