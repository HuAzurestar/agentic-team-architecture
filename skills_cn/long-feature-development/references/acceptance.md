# 面向用户的验收

准备、展示或记录验收决定时读取。验收属于任务类型或任务段落，brief 与决定保存在持久任务中，不放进 gists/，也不新建顶层 acceptance 模块。

## 准备简短决定说明

明确指定确认者及有效权限，然后用自然语言说明：

- 本次验收的业务结果、范围与排除项；
- 准确候选及适用的 requirement/solution 版本；
- 改了什么、如何查看结果；
- 条件、实际执行的检查、证据与已知限制；
- 剩余风险或待办；
- 具体请求什么决定，以及决定允许什么。

关联持久任务和设计点。内部 ID 和原始日志只是可选追溯信息，不是用户作决定的知识门槛。本文件规定材料与答复的记录内容，不规定何时、通过何种渠道主动联系用户；这些由外部 orchestrator 的作业方法决定。只有用户决定被配置为阻断前置条件时，使用 [GATE 交流协议](gates.md)，不在验收类型中另绑一套交互流程。

## 保存实际答复

确认者可以接受、拒绝、要求修改，或指定检查后暂缓决定。目标与含义明确时，自然语言有效。保留来源、范围、候选、结论、实际确认者、时间和理由；含糊回复应澄清，不能编造批准。

确认者可以是人或按外部委托有权判断的代理。准备 brief 不产生决定权限。待决定或暂缓必须保持可见，任务执行状态与验收结论分开表达。

只有委托完成条件及持久记录满足后才能完成验收任务。拒绝可以完成“处理决定”的委托；若委托要求最终决定，仅暂缓并不满足完成条件。后续工作应明确保留。

## 准确传递决定

验收只适用于已标明的候选与范围，不覆盖未来版本或全部发布动作。候选变化后评估适用性，并按外部策略决定是否需要重新验收；保留原 brief 和决定。

GATE 若依赖验收，应关联实际决定和依据；任务 DONE 本身不等于正向验收。brief 和决定都不授权未请求的合并或部署。
